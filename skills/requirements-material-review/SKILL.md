# 从资料整理待确认需求

用于已获授权的需求资料工作区。当前资料和用户原话优先；大型储能云平台是理解背景，不是必须补齐的功能清单。产物是供产品经理核对的建议，不是已批准的需求或已完成的验收。

## 读取工作区

先读 `input-index.json`，取得实际文件位置和范围；再读 `business-draft.schema.json` 与 `current-workspace.json`。技能通过显式 skill root 加载，不依赖其他全局技能。

- Word 资料优先调用 `read_document`，`file_path` 使用索引所列原件路径，即使原件没有扩展名。工具以原始标题识别格式，在宿主限定的临时目录中通过本机 Office 只读读取；模型不能选择执行程序、输出目录或工作区。通读返回的全部正文和表格，再按工具给出的已有图片路径调用 `read_image`。
- `read_document` 只有位置和正文都精确匹配才返回可引用的 `source_ref`；`unbound` 内容必须记录未绑定，不猜别名。工具列出的旧 Office 派生图不是本次新图片的匹配结果。图片未读或缺失、正文未绑定和页面未核验分别记录。
- `material-text.md` 和 `materials/` 是冻结的既有提取记录，用于回查位置及引用。Word 工具失败时可以读取这些记录，但必须明确写成“使用已有提取记录，未完成本次原 Word 读取”，不能冒称直接读完 Word；工具失败不是业务内容不存在。其他文本资料按自然顺序通读，避免只看检索命中的几个字或旧摘要。
- `source-map.json` 对应每个 `source/locator` 别名的真实来源与片段。输出复制同一记录的成对别名，不能拼接另一文件的来源与位置。
- `images/` 保存原图；使用 `read_image` 核对影响本次需求的界面、控件、文字及页面关系。图文可能互补或矛盾，不能把一张图的控件挪到另一页面。未看、看不清和截图没有表达交互是三种不同限制。
- `originals/` 保留非图片原件供追溯；可能按来源 ID 无扩展名保存以保留原始字节。不要重命名、改写、解密，或把原件存在、文件上传成功及图片占位文字当成内容已读取。需要的内容仍无法取得时，明确记录限制。
- 已存条款、问题和建议用于保持身份、避免重复；它们不是新的原始事实。用户已保存的原话可用于起草，但不意味着相关问题全部解决。只读资料，不修改原件、不运行脚本、不访问工作区外项目或外部网站。

工具单次读取被截断时继续读取剩余部分；不要将局部读取记录成完整覆盖。按工作区索引清点资料，围绕本次需求使用图像工具，不把未读区域补想出来。

## 先整理已知，再提出剩余决定

以一个独立功能为一行。对已有功能使用其 `row_key`；新功能才使用 `new-` 开头的本地名字。既有规则只是在解释本行权限或行为时，优先整理进该行，避免把每个规则重复建成独立功能。

对照全文和图片提取已描述的操作者、入口、数据、流程、权限、结果与异常。已有明确事实即使尚未写进字段，也应先形成待确认草稿，不让产品经理重新回答材料中已有的答案。

目标是大部分初稿可以直接核对使用，减少人工补写和重复确认。先复用现有需求与已答问题；已有功能中的操作、指标或详情不要换个标题再新建需求。需要建议时起草具体内容，不只留下“待确认”。普通建议与同一条需求一起核对，不为每个字段或验收分别创建一次确认问题。

逐字段区分：

- `fact`：资料明确描述的内容，附真实引用；这是模型的资料判断，仍待人工核对。
- `recommendation`：建议方案或推荐回答；即使参考了资料，也不说成已经决定。
- `unknown`：尚未说明的部分，具体指出缺什么；未知不等于没有或不适用。

一个维度中部分已知、部分未知时，把已知部分写成有来源的业务内容，未知的独立决定放到问题或限制中。例如已知失败结果但未知提示文案，不应把整个失败结果标为未知。缺失但贴合本行场景、可以合理建议的前置条件、流程、异常处理与验收，先给 `recommendation`，让人修改或随整条需求确认；无法提出有意义方案时才保留 `unknown`。不为了填满七个维度添加无关内容，也不把仅影响实现细节的空缺强行变成业务阻塞。

关键权限、收益或计费口径、控制操作、删除影响等有实质业务取舍的部分，集中突出为待决定问题，提供简洁方案但不替用户作选择。没有来源的方案只能是建议，不能通过加一个真实引用就变成事实；未知、没有、不适用保持区别。

验收描述本行可以观察到的动作及结果。页面入口可以说明点击后到达哪个页面或对话框；不要顺带展开另一功能的内部保存流程。只看见按钮不能证明点击效果、权限或默认规则；有必要提出这些方案时必须标 `recommendation`，不写成 `fact`。建议性验收引用相关场景材料作为起草依据，新增的假设仍是建议，并不因有引用就成为资料事实。没有真实场景依据时保留限制，不伪造引用。

问题只问一个可独立回答的决定。先检查原文和当前已答问题，避免重复追问。需要推荐回答时放入问题的 `recommendations`，明确其建议性质，用户未选择的推荐不能写成答案。

## 输出

最后仅返回符合 `business-draft.schema.json` 的一个 JSON 对象，不加 Markdown 围栏，不写文件。根字段必须保持 `summary`、`summary_fields`、`requirements`、`limitations`，不要新增读取报告、状态或版本字段。

只输出业务内容、本地 `row_key` 和引用别名；数据库编号、修订版本、采纳状态、关联关系和答案应用状态由程序处理。局部完善时只输出指定需求行，`summary_fields` 为 `{}`。不改写人工已确认内容，不宣称需求已完成或已自动采纳。

在现有 `limitations` 字符串数组中如实注明实际读取覆盖、未读取或不清楚的图、材料冲突及剩余未知。摘要也应反映这些限制。检查重复功能、重复问题和每条引用是否支持相应句子；来源存在本身不等于该句业务含义已经证实。
