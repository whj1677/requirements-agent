## 现场原因

本次“分析不动”并非 API 死锁：服务能正常响应，任务在首次模型调用前进入 `paused_budget`，调用数为 0。Word 已提取文字及 11 张图片，首批 3 张图的 base64 传输串被误当作文本字符计入上下文预算。只读复算：旧估算 1,149,850 字符；拆开图像传输后为 66,891 文字字符与 36,000 图像容量预留，原可用字符额度为 328,000。此复算未向模型发送材料。

前端把暂停原因放在折叠详情中，状态又在很长的第一步表单上方，导致点击按钮时难以发现失败。导入接口本身已将 Office 读取放到工作线程，但页面只有固定等待文字，没有上传和解析阶段的区别。

用户随后明确要求取消预算，因此最终策略以本节之后的“不设人为预算”为准；前面的旧预算计算保留为根因证据。

## 不设人为预算

新任务不使用累计调用数、字符估算或整项任务时间额度阻断执行。历史 `max_calls`、`context_chars`、`action_seconds`、`fixed/function_first` 设置兼容读取，但不会恢复新任务的预算限制。日常设置移除这些控件；使用量和费用仍按实际证据记录，未知费用保持未知。

保留模型单次输出能力、单请求超时、至多两次网络重试和两次格式修复、用户取消、数据发送授权、版本冲突与业务保真检查。已知 DeepSeek 模型明确截断时，可将单次输出提高到该模型已记录的物理上限后重试一次；仍不完整则不采纳。供应商报告上下文超限时明确提示分段处理，不伪造成功或默默删除原文。

当前 DeepSeek 能力复核来源：[模型列表](https://api-docs.deepseek.com/api/list-models/) 和 [Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)。这不是无限模型上下文；本文不宣称已实现任意长度文档的自动分段合并。
