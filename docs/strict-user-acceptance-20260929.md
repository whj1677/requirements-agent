# 需求 Agent 严苛用户体验验收 · 2026-09-29

> 后续状态：用户授权后，UX-01 至 UX-10 与表列四项风险已完成代码整改及本报告范围的复验。具体证据、限制及日常工作台恢复见文末“修复结果与复验”。下文原审查结论保留其历史身份，不替代新一轮独立用户整程验收。

## 验收结论

**本轮普通产品经理独立使用的体验验收不通过。** 当前适合有人指导的试用，尚不足以交给新用户自行完成需求整理、澄清和文档交付。

主要障碍是修改后的输入语义不可靠、回答草稿可能被清空、状态与阻塞提示缺乏一致解释。界面配色、卡片和基本布局已有统一风格；下一轮应优先解决操作闭环和信息层级。增加模型输出长度不能解决这些问题。

这是当前界面的有限范围验收：本轮没有修改功能，也没有证明所有分支都可用。以下区分网页复现、真实模型结果、代码确认及设计判断。

### UX-01：我改的是当前诉求，系统却把两版当成冲突材料

**复现**：在同一个首步表单先保存“备注必填，最多 120 字”，再将原字段替换为“最新决定：备注选填，最多 200 字；超长阻止保存并保留输入”。资料库和分析预检出现两份都有效的《本次诉求.txt》。真实分析把两版同时引用，要求用户重新裁决必填性、字数及超长行为。

模型生成了“联系人备注的必填性与长度上限以哪份材料为准？”等阻塞问题。用户已经完成一次修改，系统却要求他再次解释为什么改；长期使用还会积累更多旧资料。

**原因定位**：`app/main.py:378-388` 每次保存新增来源，并把所有未排除来源写入首步来源集合；`app/actions.py` 规划与执行继续读取活动来源。模型没有拿到可靠的“当前首步版本”语义。

**整改建议**：首步输入有唯一当前版本，历史版本可追溯；编辑替换自动更新当前版本身份。不能笼统删除其他独立附件，或让模型自行猜时间先后。

**复验条件**：连续修改三次，分析只使用最终首步版本；独立附件仍保留；查看历史能找到旧版本；结果不再因已替换的首步输入制造冲突。

证据：[两份当前诉求进入预检](../evidence/strict-ux-review-20260929/02-duplicate-goals-preflight.png)、[调用及合成项目摘要](../evidence/strict-ux-review-20260929/synthetic-analysis-evidence.json)。

### UX-02：“保留未知”实际删除了我刚写的调查备注

**复现**：待答问题中输入“暂存：200 字符应该合适，但需要向同事核实计数口径”，再点“暂不确定，保留未知”。文本立即清空，没有确认或撤销，保存回答按钮不可用。

`web/src/product-flow.tsx:72-78` 将回答从本地草稿删除；未知标记也是组件内状态，不是保存的决定。不能把这个按钮解释成已经替用户保留了调查进展。

**整改建议**：允许“暂未决定 + 备注”独立保存，保留原输入；如动作确实是放弃草稿，必须明确表达并提供确认或撤销。

**复验条件**：未知、保存、切换步骤、切换项目及刷新后，已保存的未知状态与备注保持；任何清空已有文本的动作可预期、可取消或撤销。

证据：[操作前](../evidence/strict-ux-review-20260929/07-answer-before-unknown.png)、[操作后](../evidence/strict-ux-review-20260929/08-answer-after-unknown.png)。

### UX-03：到底是核对完了，还是还欠五个问题？

**复现**：打开“体检试用 · 任务批量导出（Kimi试用）”的 PRD 评审页，页面同时提供以下状态：

- 顶部“当前文档已核对”；导航“需重新核对”。
- 正文“还有 5 项未澄清，暂不能下载”，要求先回答再更新。
- 右侧“未决事项 0 项”“本期没有待答问题”。
- 五条拦截原因全部是“已保存回答尚未完整纳入关联产品条款，请先核对采纳”，没有问题标题或各自定位入口。

后台可能分别统计文档核对、未回答问题、回答未纳入条款。**本轮发现的是这些含义没有在界面讲清楚，不能直接据此断言底层数据互相矛盾。** 用户看到的是“没有待答问题，却让我先回答”，很难自行完成。

**整改建议**：提供一个总览，分别说明“待回答”“回答待纳入条款”“文档待更新/核对”；每个阻塞列明问题名称、关联内容与直接处理入口。全部区域使用同一准备状态定义，历史核对不能表现为当前交付已就绪。

**复验条件**：用已回答但未纳入条款的项目验收，提示应为“5 条回答待核对纳入”，可以逐条跳到处理位置；处理一条后所有区域同步更新，最终没有互相打架的总状态。

证据：[文档评审页](../evidence/strict-ux-review-20260929/11-document-review.png)、[包含右侧滚动内容的完整页面文字](../evidence/strict-ux-review-20260929/document-review-dom.txt)。

### UX-04：我请你帮忙完成当前步骤，你要求我先完成当前步骤

在第二步需求详情点击“帮助澄清此项”，输入要求并进入任务预检后，才看到运行按钮不可用，理由为先完成第二步的现状、价值、范围等核对。前面的帮助入口没有提前说明限制。

**整改建议**：入口旁直接解释当前可做的帮助。若帮助会修改尚在核对的候选，应允许生成候选并保留必要确认；若业务门禁必须限制执行，则在打开前说明缺项，并提供就地补全。不要让用户写完一遍再走回头路。

**复验条件**：第二步尚未核对时使用帮助，要么完成明确范围的辅助任务，要么在输入前知道限制并可直接处理；输入不丢失。

证据：[写完求助内容后的阻塞弹窗](../evidence/strict-ux-review-20260929/06-help-blocked-by-current-step.png)。

### UX-05：结果已生成，主操作仍然像让我重做

本轮分析结束为 `partial`，已有需求、规则和澄清问题，但页面停在首步，重新启用“分析现状与诉求”，同时出现“查看已有分析结果”和“查看分析结果”两个相近入口。“仍有限制”的具体原因折叠在执行记录里。

`web/src/workspace.tsx:78-88` 只对 `succeeded` 自动进入下一步。本轮不代表成功分支没有自动跳转，也不要求把真正失败的任务当作成功。

**整改建议**：按结果是否可供用户核对决定下一动作。有可用结果时，将“核对整理结果”设为唯一主操作，并直接提示仍缺什么；重新分析成为次要操作。确实无法继续时，给出具体失败原因和恢复入口。

**复验条件**：成功、有可用结果但有限制、失败三种状态各有清晰的主操作；用户无需猜测任务是否结束，也不会因停留原页误发第二次分析。

证据：[有可用结果后仍停留首步](../evidence/strict-ux-review-20260929/04-analysis-finished-still-step1.png)。

### UX-06：核对业务前，需要先学会系统里的多套状态

第二步同时出现“候选未采纳”“本期范围勾选”“分析建议待核对”“保存范围草稿”“确认范围”。条目已经显示稳定 REQ 编号，但拦截提示仍说“尚未形成带编号的独立本期需求”；实际还需要把条目选入范围。第三步则把多串 Q/REQ/RULE/AC 长编号直接放进问题阅读区。

这些状态在数据层可以有区别，用户任务层却缺少明确的次序和结果解释。现状、目标、保持项卡片占据大量空间，真正缺项和本期需求要向下找。

**整改建议**：按“核对整理内容 → 选择本期需求 → 查看剩余缺项”组织，主要展示业务名称和短编号。保留采纳语义，但不要让普通用户必须理解底层状态字段。错误提示精确指向尚未勾选/尚未核对的对象；按钮可直接带到相关位置。

**复验条件**：已有候选但未勾选时，明确提示“请选择至少一条本期需求”；缺少价值或优先级时可直接编辑对应字段；不会再把“未选入范围”描述成“没有编号”。

证据：[范围核对实际页面](../evidence/strict-ux-review-20260929/05-scope-review.png)、UX-04 预检中的具体缺项。

### UX-07：我来找附件，却先看到一整屏导入配置

“项目资料”抽屉先显示工程上下文 JSON 导入、材料用途、普通文件导入和辅助输入，已有资料位于下方。在本轮视口里，需要接近一屏才能看到资料卡。两份同名《本次诉求.txt》均显示已读取，缺少便于区别的版本或时间摘要。工程包入口还使用原生文件控件，和普通文件入口样式不一致。

**整改建议**：默认先显示现状、目标诉求、设计参考等已有材料，提供紧凑的“添加资料”；导入表单按所选类型再展开。工程上下文仍是独立类型，但无需长期占据资料列表首屏。重复文件显示时间/版本与简短内容摘要。

**复验条件**：打开资料即可看到分类和已有文件，能在不逐个打开的情况下区分同名版本；添加 Word、截图和工程包的入口均可发现。

证据：[资料抽屉](../evidence/strict-ux-review-20260929/09-material-library.png)。文本预览自身已较简洁，见[当前阅读器](../evidence/strict-ux-review-20260929/10-source-preview.png)；不建议恢复用户此前反感的“段落 1、段落 2”展示。

### UX-08：正文阅读和内容核对被多栏、长日志打断

当前视口中，项目侧栏之外，文档又分目录、正文、审查侧栏；几处分别滚动。正文变窄，右栏长审查意见频繁断行，混有长 ID、`selection_status=selected`、`epistemic_status=inferred` 等内部表达。

界面要求“章节与来源核对”，但正文条目缺少直接打开关联条款/原文的入口；章节仅有“讨论此章节”。用户要记住编号，跨步骤找来源。`web/src/workbench.tsx:54-61`、`web/src/panels.tsx:29` 可确认当前阅读节点和侧栏实现。

**整改建议**：正文占主要空间，目录和审查面板按需展开。审查意见按“问题—影响—处理位置”展示，技术细节折叠；在相关段落就地标记意见、提供条款与来源跳转，并保留阅读位置。内部审查过程继续留在评审区，最终文档正文保持纯净。

**复验条件**：在本轮相同视口下能连续阅读正文；点击某条审查意见可定位原段落及来源，返回后位置不变；用户不必复制长编号去别处找。

证据：[文档页面与多处滚动区](../evidence/strict-ux-review-20260929/11-document-review.png)。这次浏览的是历史已生成稿，不能据其篇幅或旧附录审查意见判断最新生成器的 MRD/PRD 质量。

### UX-09：新用户配置模型的必经操作被称为“高级”

模型设置初始页面大部分空白，基础地址、模型、Key 输入及测试都藏在“高级模型配置、密钥与连接测试”里。展开后又先出现 max_tokens、环境变量名、JSON 输出、结构化推理等配置。页面明确说明 Key 只临时生效，持久保存需要手工编辑 `.env` 并重启。

**整改建议**：基础区只保留接收端/模型、Key、安全保存与连接测试，配置状态清晰可见；其它开关折叠。持久配置沿用现有受保护凭据能力，避免普通用户必须编辑工程文件。保留材料发送授权的独立含义。

**复验条件**：首次用户只通过网页完成配置、测试，重启后仍可使用；界面明确说明保存范围。安装包是否另有配置入口，本轮未验收，不据此宣称所有入口均不可用。

证据：[初始设置页](../evidence/strict-ux-review-20260929/12-model-settings-collapsed.png)、[展开后的设置页](../evidence/strict-ux-review-20260929/13-model-settings-expanded.png)。本轮没有修改模型配置或 Key。

### UX-10：项目多了之后，不容易回到上次工作

原有 14 个项目中有多个同名“测试”。侧栏只有名称，没有搜索、阶段或更新时间；长名称频繁折行。刷新后回到“选择或新建需求项目”的空白引导，不恢复当前项目。`web/src/main.tsx` 当前项目只保存在组件状态中。

**整改建议**：保留上次项目和阅读步骤；项目列表显示最近时间、当前阶段，提供搜索。首次空白页给出清晰入口，已有项目时优先展示“继续上次工作”。

**复验条件**：刷新后能回到原项目；同名项目可按时间/阶段辨认；大量项目可搜索定位。此建议不等于本轮证明刷新丢失了所有草稿。

证据：[恢复日常工作台后的项目列表及空白主页](../evidence/strict-ux-review-20260929/14-daily-restored.png)。
