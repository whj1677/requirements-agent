# 成文检查：确认已有修改

> 后续界面已统一为整表确认，当前操作见 [使用说明](user-guide.md#成文检查用一张表集中确认)。下文保留本阶段实现与验证记录。

## 这次问题

“bms统型”项目已保存业务回答及后续“是”，但三个修订候选尚未替换旧条款。旧界面把技术编号、原文定位、重新调用助手、直接修改等选项同时展开，无法清楚说明下一步。

失败检查还暴露了两处程序缺口：摘要 `product_context.current_state` 的真实引文没有被成文检查解析；模型把 `required_decisions` 中的必答问题标成了普通 warning。原任务失败记录及模型原文保留，不改写历史成功状态。

## 新处理路径

1. 成文检查明确提示“检查未完成，回答已保留”，旧检查项继续保留供处理，技术详情折叠显示。
2. 若检查建议明确引用了当前已有修订、修订关联到本项真实条款且回答已保存，显示“已有修改，等你核对确认”。
3. 点击“查看已起草修改（不调用 AI）”，查看原文、修改后、全部业务说明、来源、详细定义和已保存回答。
4. 点击“确认这些修改”，在同一事务内保存已展示条款，同时落实原业务回答及其后续确认回答。未点击确认前不修改业务数据；回答、来源或候选变化后旧预览不能提交。
5. 保存后再点击“重新进行成文检查”，在任务弹窗核对范围后运行。此时检查的是修改后的版本；这一步按当前模型配置计费。

既有候选不完整、关联模糊或已变化时，不推测要采用哪份修改，保留原有处理入口。必答问题仅在问题原文精确相同（可附括号选项）且关联唯一时提升为阻塞项，不用语义相似度猜测关联，不替用户决定选项。
