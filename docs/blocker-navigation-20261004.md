# 阻塞点处理入口与验证记录（2026-10-04）

## 问题与结果

第三步原先用长列表展示缺失内容和条款编号，用户无法从阻塞说明找到对应的编辑、采纳或验收操作。第五步部分跳转还依赖错误文案中的关键词，容易指向不相关位置。

现将当前阶段阻塞按需求或问题分组，每一项附上明确的处理入口。点击后展开对应内容、滚动并聚焦处理位置；条款和字段使用一致的高亮。处理时可返回原阻塞清单。保存后依据最新项目重新计算清单；不能继续时也回到同一清单。

## 操作映射

| 阻塞原因 | 入口与处理位置 |
| --- | --- |
| 业务行为缺项 | “补全业务行为”：展开对应需求，聚焦第一个缺失字段 |
| 没有已采纳的关联验收，但已有相关候选 | “核对关联验收候选”：仅定位该需求的相关验收候选，由人审核后采纳 |
| 没有可核对的关联验收候选 | “补充关联验收条件”：打开填写窗口，预选对应需求 |
| 已保存回答尚未落实到条款 | “核对已保存回答”：重新读取对应回答的核对结果并打开核对窗口 |
| 问题未回答 | 直接定位对应问题及回答输入框 |
| 本期需求或范围未明确 | 定位对应需求的范围、行为或采纳操作 |
| 文档缺失、过期或待核对 | 打开对应 MRD/PRD，聚焦生成、阅读或核对入口 |
| 前序阶段未完成 | 返回实际需要完成的阶段及其阻塞清单 |
| 语义审查阻塞 | 打开当前审查问题的处理入口 |

入口来自后端明确的条款、问题、字段及文档标识，不再解析错误文本猜测位置。目标已变化时要求重新载入项目，不会定位到无关条目。重复说明保留全部有效入口；同名但不同编号的需求不合并为同一个处理对象。

## 保持的业务边界

- 阶段核对、正式确认的条件、消息顺序及业务哈希不变；阻塞清单与原缺失消息由同一个投影生成。
- 点击处理入口只导航、展开或读取；不会自动采纳、确认回答、填造业务规则或调用模型。
- 采纳、保存及记录回答仍需用户明确操作。补充验收先保存为候选，仍需审核采纳。
- 页面中未保存输入仍由既有离开保护处理；返回阻塞清单不绕过草稿保护。
- 没有替用户消除本项目的 30 个阻塞项；本次交付解决的是找不到操作位置的问题。
