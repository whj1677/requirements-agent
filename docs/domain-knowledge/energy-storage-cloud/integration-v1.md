# 储能云平台知识接入与维护方案

2026-10-12：源码现状与用户指定的 [基础概念](common-concepts-v1.md) 共用知识已按用户授权接入，实际方案、版本更新与输入边界见 [当前共用知识说明](source-baseline-20261012.md)。基础概念在活动 JSON 的 overview 中首次完整注入，不需要模型二次检索。本文件主体保留此前行业知识的评审方案；原完整行业草案未整体启用。

建议采用本地文件知识包，通过统一的上下文组装组件按需注入。第一版使用专题、别名和关键词检索，结合显式业务关联补充必要背景。更新采用新的不可变版本，保留每次请求实际使用的知识快照。

以下为行业知识包的接入评审方案。行业正文和索引目录为 0.1.0 待评审版本；这部分知识尚未启用，也未验证需求分析效果。

## 交付文件和知识身份

| 文件 | 职责 |
| --- | --- |
| knowledge-v1.md | 人工可阅读和修订的知识正文，是内容维护的唯一主文件 |
| index-v1.json | 专题编号、正文标题定位、主题词、别名、关联专题和来源；不复制正文 |
| integration-v1.md | 外挂、更新、检索与后续验收方式 |

本稿的知识包类型为 `domain_knowledge`，与已有源码导出的 `business_context` 分开。行业知识不包含公司的源码快照，不能伪造 repository、commit 或部署版本以迁就现有工程上下文 schema。

每个专题区分行业参考、分析框架或混合内容。公开来源支持的概念与作者组织的提问框架分别写明。索引条目指向正文及来源位置，正式接入时再生成片段哈希和发布清单。

## 通过什么方式外挂

### 本地文件知识包

维护稿放在本项目 `docs/domain-knowledge/energy-storage-cloud/`。评审通过后，将正文和索引生成一个版本化发布包，随应用安装提供默认版本。部署后的知识目录由一个明确配置指定，例如 `DOMAIN_KNOWLEDGE_DIR`，指向本机获准使用的知识包目录；这是拟新增配置，不是当前已支持功能。

安装版默认包和自定义外挂目录按明确优先级选择一个活动版本，不将两套内容混合使用。第一版可以采用默认包加人工替换发布包的方式，不需要额外服务、向量数据库或产品经理持有源码。通过已有启动和维护流程更新配置及应用，不建立第二工作台。

应用读取包的结构、内容哈希、发布状态和适用范围。知识正文只作为数据，不能执行其中的代码或把它当作指令。缺失或无效的包不影响需求原文保存；分析可继续但应明确本次没有提供领域知识，不伪装成已加载。没有可用新版本时保留上一有效版本，并记录原因。

### 在请求组装时加入

拟提供一个共用组件，职责为 `识别适用性 → 检索 → 按预算组装 → 记录快照`。它返回单独的 `domain_knowledge` 上下文，不把知识插入项目 `sources`、人工回答或已确认条款。

参考输入形状如下，编号仅表示知识身份，不能冒充项目证据：

```json
{
  "domain_knowledge": {
    "package_id": "energy-storage-cloud",
    "version": "1.0.0",
    "evidence_role": "industry_reference_not_product_decision",
    "route": "related",
    "overview": "本次实际提供的总览正文",
    "cards": [{"id": "ESC-ALARMS", "heading": "告警怎样进入处理流程", "text": "本次实际提供的专题正文"}]
  }
}
```

可信任务头只定义使用政策：知识帮助理解术语、关系和追问；不能自动建立当前产品现状、功能范围、数量、权限、时限或验收指标。知识编号不能填入正式 `source_refs`；若用户明确采用某项建议，应保留其实际决定，走现有来源和候选核对流程。项目中的具体事实与行业参考有差异时，核对适用条件，而不是任意择一。

### 接入当前工程的位置

只读核对当前工作区后，可见至少两条主要请求组装路径：

| 位置 | 现有职责 | 拟接入方式 |
| --- | --- | --- |
| `app/provider.py` 的 `assemble` | 访谈、整理及文档等请求组装；已有工程上下文、项目背景和资料预算 | 在当前上下文定型后、最终预算检查前加入领域知识 |
| `app/business_draft.py` 的 `_input` 和 `assemble` | 业务草稿及局部推荐的另一套输入合同 | 使用同一个组件，按当前行或本次范围检索，随后使用已有上下文预算检查 |
| `app/decision_semantics.py` 的 `build_request` | 判断已保存原话覆盖哪些决定 | 第一版不注入通用行业知识，避免用行业惯例替用户回答；仍只依据原话及本批资料 |

实施前需盘点实际调用分支，覆盖需要领域理解的入口，并检查局部任务、MRD、PRD和评审的作用域。只改一个提示词或只给聊天入口加知识，不能声称全流程接入完成。这些位置是当前代码观察，不是已经完成的实现。

## 后续通过什么方式更新

### 内容修订和审核

日常维护由我们整理差异和来源，你核对有影响的业务解释。产品经理使用需求 Agent 时不需要每次审核全部知识，也不需要找研发索要代码。

修订流程为：提出问题或新增资料 → 修改正文 → 同步调整索引 → 检查出处、范围和关联 → 核对差异 → 生成新版本 → 显式切换活动版本。

来源变化、发现解释错误、专题明显不足或收到通用性反馈时更新。第一版按需维护，不承诺自动抓取网页或定时发布。对公司专属事实，另记产品、版本和依据；不能直接覆盖共享行业知识。对话和用户反馈只形成更新候选，不自动写回全局知识库。

### 版本和回滚

已发布版本只读；修改产生新版本。发布清单包含包 ID、schema 版本、知识版本、发布日期、整包哈希、专题哈希、来源核对日期、适用范围和修订摘要。草稿不可自动进入日常模型请求。

应用在切换前验证完整发布包，成功后一次性更新活动版本指针；切换失败继续使用旧包。派生索引绑定整包哈希，正文或索引发生变化却未重新发布时拒绝使用，不能混读两个版本。

每项任务创建时冻结知识版本，运行及修复请求沿用相同快照。明确重新分析可以选新版本。版本切换不改写历史文档、业务状态或已保存决定；相关结论如需更新，走正常复核流程。回滚通过切回上一有效版本完成。

## 通过什么方式检索

### 先判断是否适用

优先读取当前用户明确说明、项目产品定位和本次任务对象，再看当前相关材料。自动判断不永久改写项目定位，历史助手回复不能作为唯一判断依据。建议保留 `auto / energy_storage_cloud / other` 项目选择，属于后续实现内容。

| 结果 | 知识输入 |
| --- | --- |
| 明确属于储能云平台 | 简短总览与相关专题 |
| 可能属于或信息不足 | 简短总览；只有当前意图明确命中的专题才追加，不自动展开全部模块 |
| 明确是其他产品或当前任务不属于云平台业务 | 不注入 |

关键词只能辅助判断。“设备管理”单独出现是待辨识；“储能”加“BMS 固件算法”也不能误判成云平台功能。对同一项目里混合的产品需求按当前目标分别判断。产品经理已经明确说明后不重复确认，每个任务可以有不同的路由结果。

第一版采用本地确定性判断，不新增专门的分类模型请求。无法可靠判断时归入可能相关，让既有访谈在必要时澄清；不靠一个随意的置信度数值假装已确认。

### 再检索相关专题

1. 构造查询：使用用户本轮原话、任务目标、局部需求及相关的已核对背景。局部完善只取当前行的语义，不让其他行或全量历史扩大检索范围。
2. 过滤：只取当前活动发布包、可用专题和符合产品范围的内容。公司专属覆盖层只在明确匹配的产品内可用。
3. 匹配：对标题、主题词和维护过的别名做中文词组匹配。先匹配完整词组；英文缩写不区分大小写，并校验词边界，避免 `SOC` 命中不相干的英文单词。
4. 排序：明确指定的专题、完整业务词组和多个独立概念命中优先；重复词不反复加分。排序规则和版本固定，以便复现。
5. 补充关联：沿索引里的显式关系补充与当前问题必要的背景，只展开一层并去重。关联是候选关系，不是必须全量加载的依赖树。
6. 控制输入：先给当前需求、已确认决定和项目证据留足已有预算，再提供总览和少量专题。第一版可从最多 4 个专题试起，含关联专题；数量是拟验证参数，不是行业事实。预算不足时先缩减或省略知识，不能截断用户依据来容纳参考资料。

中文不依赖默认英文分词器；第一版的小型索引直接使用维护过的词组和别名。零命中时给总览及明确的覆盖限制，不伪造专题命中，也不把没有检索到解释成业务不存在。不需要重新调用模型来扩大检索。

### 什么情况下增加语义检索

如果真实查询经常使用不同表达，而补充别名仍不能解决漏检，再评估本地语义索引与关键词检索组合。生成索引和在线检索的权限、成本及依赖另行核对。向量索引只能是可重建的派生产物，版本、适用范围和来源检查仍然保留。

关键词与语义匹配互补、孤立片段可能丢失上下文，可参考 [Anthropic 的上下文检索研究](https://www.anthropic.com/engineering/contextual-retrieval)。本项目先验证较简单的方法；研究中的检索效果不能当成本项目效果。

## 如何知道实际用了什么知识

每次请求由程序记录包版本和哈希、路由及理由、查询范围、实际提供的专题 ID 和片段哈希、关联补充、预算省略及加载异常。日志中的“已提供”不等于模型确实正确使用，是否正确理解还需核对输出。

最小用户呈现可以是在现有任务结果附近显示“参考了储能云平台基础知识”和可展开的专题与版本；明确未启用或加载失败时显示实际状态。引用原文可回到冻结版本的知识片段。第一版不必另建知识工作台。

## 用什么情况验收

下表是冻结的待验证预期，不是已通过的测试。检索正确性、模型理解和产品经理认可应分别记录。

| 输入或变化 | 预期行为 |
| --- | --- |
| 储能云平台增加告警恢复记录 | 提供总览及告警、监测或数据质量相关专题；不扩展为工单、短信和控制全套功能 |
| 在该平台里增加日报 | 检索报表及与目标指标相关的知识；不把日报解释为所有指标都必填 |
| 做一个餐饮点单小程序 | 不提供储能云平台知识 |
| 需要一个设备管理页面，产品尚不明确 | 仅提供总览作为暂定背景，不能认定是储能站设备 |
| 为 BMS 固件优化 SOC 算法，明确与云平台无关 | 不提供该云平台包；不会因为出现储能缩写就强制注入 |
| 项目 A 的收益重算方式用于项目 B | 通用概念可用，A 的专属规则不可带入 B |
| 需求明确说本次只做监测 | 不从知识库补出控制功能或控制验收 |
| 当前产品定义与通用术语不一致 | 保留当前定义，核对适用条件；不静默替换 |
| 索引缺失、包未发布或内容哈希改变 | 不声称已加载新知识，继续原有需求流程并显示实际限制 |
| 任务期间发布新版本 | 原任务保持原快照，新分析才使用明确选定的版本 |
| 知识超出预算或检索零命中 | 保留当前需求与证据，缩减或省略知识，不虚构覆盖 |

当前完成的是知识评审稿、索引目录和接入方案。运行接入、离线检索回归、真实模型理解验证及产品验收均为 NOT_RUN；没有为了此稿调用需求 Agent 的真实付费模型。

## 第一轮需要确认的方案选择

建议第一版采用本地文件知识包、正文为唯一主内容、人工审核后发布新版本、关键词别名检索加一层关联补充。先核对知识总览和关键业务概念，再确认上述接入方式。实施达到入口覆盖、版本可追溯和有限场景验收后收口，后续按实际漏检及误解补充知识。
