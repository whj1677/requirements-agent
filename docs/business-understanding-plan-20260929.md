## 原方案阶段目标与结论

目标是让需求 Agent 理解云平台的业务对象、参与者、场景、流程、规则及改动影响。技术架构提供实现背景。业务理解通过任务上下文获得，不等于训练模型永久记住整个系统。

本轮输入为现有生成实现、公司参考内容 profile、一个已有试用项目的文档、成熟产品文档公开指引以及云平台归档的一个静态业务切片。交付为这一份实施方案。验收是解释当前限制、明确最小导入契约、设计具体使用路径及可观察的验证标准；到方案完成停止，不修改日常项目、运行服务、调用付费模型或实现新功能。

建议把“业务背景包 + 有来源的需求深化 + 分别生成 MRD/PRD”作为一个闭环做。只增加导入文件，不能解决当前成文阶段只能重新组织条目的限制。第一版只对一个业务切片跑通完整闭环，随后按需扩充业务覆盖。

## 对照成熟文档，应该增加什么

公开资料用于校准内容职责，不替代公司模板，也不作为云平台业务事实。Atlassian 的 PRD 指引强调目标、用户故事、交互、假设、成功标准和范围边界，同时要求适量清晰；Aha! 的 MRD 指引强调目标市场/客户、需求依据、替代方案、能力方向和衡量方式。成熟不等于篇幅长。

| 文档 | 本项目应该写清 | 应从哪里取得 |
| --- | --- | --- |
| MRD | 哪类用户在什么场景遇到问题；现有处理方式；问题影响和需求依据；为什么值得做；目标、优先级、范围、成功衡量及相关业务影响 | 用户输入、访谈/运行数据、已有产品资料、经核对的业务背景；市场规模、客户收益和真实使用频率不能从代码推断 |
| PRD | 每项改动的操作者、入口、对象/字段、正常与替代流程、状态变化、权限、业务规则、失败后的页面和数据结果、上下游影响及可观察验收 | MRD 目标、本次确认的业务决定、原型和现状、经核对的业务背景；实现细节由工程设计承接 |

对于存量云平台的小改动，MRD 可以是一份精简的业务价值说明。没有市场研究时，不强填市场规模/竞品/收益，不把小功能强行升级为新产品立项。PRD 的细度随数据、权限、状态及跨模块影响增加；适用性有依据，不机械填写所有维度。

参考：[Atlassian PRD 指引](https://www.atlassian.com/agile/product-management/requirements)、[Atlassian PRD 模板](https://www.atlassian.com/software/confluence/templates/product-requirements)、[Aha! MRD 内容与模板](https://www.aha.io/roadmapping/guide/templates/market-requirements-document)。

## 一个导出物：业务背景包

拟创建 `export-business-context` Skill，在用户指定源码目录执行。对外交付只有 `business-context.json`，导入 Agent 后展示人可读概览。Skill 内部可以维护 schema 与校验脚本，但不要求产品经理管理多份报告。

包应先给简短产品与模块全景，再提供本次相关模块的详细业务内容；技术栈、服务划分和数据存储仅保留有助于理解流程/影响的摘要。不能仅凭目录名、表名或依赖清单生成“懂业务”的结论。

建议 v1 包含以下结构。这是拟定契约，不是当前可导入格式：

| 字段 | 内容与用途 |
| --- | --- |
| `schema_version`, `bundle_id`, `generated_at` | 格式版本、包身份、生成时间 |
| `project`, `source_snapshot` | 产品身份；各仓库版本与工作树状态；无 Git 时标未知并记录所读文件摘要；部署版本另行标注，不从 Git 推定 |
| `overview` | 产品解决的业务问题、模块概览及术语，陈述引用下方事实 ID；无法确认的目标保持未知 |
| `modules[]` | 每个模块的对象及关系、角色/权限线索、场景、流程/状态、现状规则、依赖/影响，引用事实 ID |
| `claims[]` | 原子业务陈述、适用模块、来源性质、证据 ID；来源性质为 `code_observation / document_claim / inference` |
| `evidence[]` | 仓库 ID、相对路径、符号、行号、文件 SHA-256、短摘录或精简说明。代码注释、测试和实际实现分开标来源 |
| `unknowns[]`, `conflicts[]` | 未知的影响和补充方向；相反陈述及各自证据，保留双方，不静默选一方 |
| `coverage` | 已深入查看/仅有索引/未查看的模块、所读文件清单、排除范围、仅静态检查等限制 |
| `technical_summary` | 精简技术框架及业务流程关联；不输出类/接口/数据库全量清单 |

导出内容是现状线索及实现观察，不自带“业务已确认”权力。是否采信、适用于本次需求、进入规范，由需求 Agent 中的确认记录控制，不能相信导入 JSON 自报的 `approved=true`。

### 源码侧的执行方式

1. 只读识别工程边界、多个仓库和未提交修改，遵守适用项目规则。读取业务说明、菜单/路由、页面调用、控制器、服务规则、业务对象及相关测试，建立模块索引。
2. 沿一个真实场景追踪“页面动作 → 接口 → 业务处理 → 数据对象/状态 → 返回结果”。前后端调用相接但未实跑时标静态关联，不能称为已验证运行流程。
3. 提炼可引用的业务陈述和关键关联。对未找到的内容标“未确认”，不能把“没搜索到”写成“不支持”；代码缺陷不自动变成正确业务规则。
4. 校验引用存在、行号/文件摘要与快照一致、关系 ID 不悬空、来源与不确定性可追溯。语义仍需独立检查，哈希只能证明内容身份。
5. 只写输出文件，不改源码、不启动项目。排除密钥、环境凭据、数据库原始数据和构建依赖。材料进入执行 Skill 的模型时仍遵守所选工具及组织的授权边界，不能把“本机运行 Skill”描述成源码绝不会进入远端模型。

### 云平台切片已说明这个方案有用

有限静态检查已确认：归档包含多个后端仓库；前端目录没有自己的 Git 信息。选查的电价后端工作树有未提交修改。因此包必须记录逐仓版本与所读文件快照，不能只写一个“项目版本”。

在电价模板/园区电价切片中，前端代码包含把模板应用到多个园区和目标月份的调用；后端控制器声明批量配置及对应权限码；业务对象保留模板来源关联。它可以为“模板批量应用”需求提供更具体的问题：已有配置如何处理、目标月份如何选、谁有权操作目标园区、模板后续变化是否影响已应用配置，以及部分失败怎样反馈。这里的问题是需要澄清的候选，不是源码已经给出的答案。

## 需求 Agent 内的使用路径

1. 项目资料新增“业务背景”入口，上传这一个 JSON。展示产品名称、生成时间、适用版本、覆盖模块和读取范围，以及“对业务的理解”概览。
2. 产品经理选择本次相关模块，例如电价模板与园区电价。Agent 先给出简短现状复述及重要冲突；逐项更正关键错误即可，不要求审批所有代码观察。
3. 默认用包帮助理解和提问；只有被本次需求采用的关键业务规则需要确认。导入、允许模型读取、采信现状和采纳本期需求是不同动作，沿用既有授权/采纳机制。
4. 发起分析时带入“产品概览 + 所选模块 + 明确关联的上下游 + 本次需求”。先按显式选择和业务关联选内容，需要其他模块时提示原因；第一版可直接按结构化 ID/标签检索，不引入向量库。
5. Agent 给出“当前理解 / 本次变化 / 保持项 / 影响 / 高价值待确认项”，提出有来源的深化候选。包中未知不能变成肯定陈述，已有答案不重复盘问；新增决策记录到当前需求，不倒改历史包。
6. 首版保留包版本，只有用户明确切换才激活新包；切换或禁用时将依赖旧包的当前分析/文档标为需要复核，保留历史快照与引用。逐事实差异和精确影响清单列为后续增强，不作为第一个场景闭环的前置条件。

状态转换必须明确：`code_observation / document_claim / inference` 都只处于“可供分析”状态，可带来源和不确定性用于复述现状线索、提出问题或生成候选。选择模块只表示相关性选择，不等于确认事实，也不自动扩大既有模型读取授权。进入已核对 `product_context` 或正式文档事实前，须有针对具体陈述的用户确认；进入本期规范须另经候选采纳。无须确认全部代码观察，未被采信的观察保留在背景中，不能被悄悄改写成确定事实。

## 让文档变深的生成机制

采用“理解并核对 → 深化相关业务场景 → 分章节成文 → 检查遗漏与保真 → 人工确认”。

- 业务深化先产生可核对候选：场景步骤、状态变化、规则条件/结果、数据来源、异常和关联影响。依据来自需求材料、业务包及本次回答；确实缺少业务决定才提问。只记录通用框架中的空字段不能当作深化完成。
- MRD 形成问题与价值论证、受益角色、需求依据、目标/成功衡量和能力范围。PRD 从这些目标展开每个功能的操作及结果、规则、数据、权限、异常和验收。继承公司模板，允许合理合并章节。
- 成文增加受控的解释性块：每段/表格注明所依赖的事实、已采纳条款和快照版本。模型可以组织解释和流程说明；凡新增数值、权限、默认行为、承诺或规则，必须退回候选/待决，不能悄悄写进正式正文。
- 规范核心继续受程序保护，同时检查解释性正文是否扩大、弱化或反转原规则。讨论过程、工具状态和审计信息留工作台，不混入产品文档。
- 长文按业务章节分批生成，每批固定相同底稿、背景包及确认版本，再做跨章节一致性检查。只对失败章节重试；输入版本变化时使相关候选过期，不能把不同版本拼成一个“通过”的文档。

MRD 的业务价值来自业务证据，现有技术限制可作为实施约束和风险单列。已有系统做不到，不能据此否定需求价值；代码现有行为也不能自动规定未来行为。这些边界保护文档的客观性。

## 建议实施顺序与验收

先选“电价模板应用到园区”作为一个闭环试点；角色权限、覆盖及失败策略以业务确认结果为准。这是建议试点，尚未冻结其产品规则。

1. **业务包纵向闭环**：做可在源码目录运行的 Skill、单 JSON 校验、业务背景导入/选择和引用；验证 Agent 确实收到选中的相关业务内容。
2. **业务理解深化**：加入场景与影响候选，让用户能纠正现状、回答重要问题，并追踪到本期规则；保护已有回答和未确认状态。
3. **MRD/PRD 分别成文**：开放带证据的解释性生成及结构化展开，完成保真和独立场景检查；与旧机制对照后再扩大到其他模块。长文分批只在所选场景超过单次容量或确有截断时纳入本次实现，不为一个小场景先建设完整长文调度机制。

每项按顺序独立验收。阶段 1 的最低闭环是“真实导出一个包 → 导入并选择模块 → 分析中实际使用了指定事实且引用可追溯”；无需等新文档机制完成才能验证它。阶段 2 验证业务理解是否改善，阶段 3 才验收成文质量。首版复用既有资料/候选/确认能力，以必要适配为主；不重构无关工作流。

首版验收不设字数或页数门槛：

- 同一需求先做不带业务包的基线，再带包对照，冻结模型/输入版本。Agent 能准确解释所选业务对象、关系和已知流程，区分现状与本次改动；不能只复述 Java/Vue 等技术栈。
- 已有事实能正确回答并追溯；资料真正没有答案时保留未知；文档与源码冲突明确显示；没有读到的模块不能自称已覆盖。
- 所有明确适用的业务场景在文档有清楚结果或具名待决项。产品、开发、测试分别根据同一需求解释正常、边界、权限及失败场景，应得出一致预期；这部分业务答案须由用户/业务方提供或确认，不能全部从同一模型生成后互相背书。
- MRD 能回答“为什么、为谁、价值依据与怎样衡量”，PRD 能回答“怎样操作、什么条件、什么结果、如何验收”；不能只是同一批正文换章节位置。
- 新功能如与旧实现矛盾，应明确本次改变及影响，不能自动偏向旧代码；旧 bug 不作为产品要求。
- 原文、来源身份、确认/采纳边界、已有交接与回滚能力保持；导入失败、损坏/不支持版本、取消、重复导入、更新/禁用及恶意指令内容都有清晰行为。结构校验成功不等于业务验收成功。
- 大包按模块取用，超过模型上下文时明确分批或遗漏，不能静默截断；全过程记录真实调用、输出及用量，费用未知则如实记录。
