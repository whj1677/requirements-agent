# PRD 成文可靠性修复（2026-11-13）

基于 `codex/dpi150-20261030` 的 `9f5a612dfa5090de936fc12e2be4679713cad0cf`。

## 问题与修改

1. 程序从已保存需求编排的章节，误用了模型建议的 `explanations.maxItems=12`、`text.maxLength=1200` 限制。13 条基础需求或较长行为描述会确定性报 `SCHEMA_INVALID`。现在分别处理模型自由建议与程序保存内容；本机入口显式选择保存内容编排，混合详细需求、流程未知的评审稿也适用。固定章节的模型 schema 与实际固定值保持一致。
2. 最终文档的解释块可容纳两项各最多 6000 字符的行为字段及中间换行，共 12001 字符。原文完整保存，继续执行来源、引用和语义校验；模型自由计划仍保留原有 12 条、1200 字符限制。规范条款与来源说明作为一组，按每章 100 块限制分章，覆盖映射指向实际所在章节。
3. 当前成文检查通过，或允许保留未决事项且没有硬阻塞时，常规 PRD 入口使用已有本机成文服务。正文不依赖新增模型流程图成功。成文检查页保留明确的可选 AI 绘图入口，沿用空任务消息，避免操作提示被存成新业务来源、使有效检查过期。
4. 旧图仅复用当前交付范围内、仍已确认且来源指纹匹配的基础需求。移出本期的需求不会因为旧图被带入而使整份新 PRD 报错。
5. 同一预览提交失败后重试，继续使用相同的幂等键、版本和预览哈希，复用后端已经完成的生成结果。

未决事项、过期检查、来源及结构问题的门禁继续生效。生成文档不等于正式交付确认。

### F1：成文检查要求全覆盖，但检查响应最多只能引用 100 个规范条目

**影响：合法保存的项目可能无法完成当前版本成文检查。** 这里计算的是需求、规则、验收三类条目的合计，不是仅计算需求数。

最小补证路径：从已有 100 条本期需求的隔离项目出发，调用实际 `POST /api/projects/{pid}/items` 新建第 101 条，再通过实际条目保存接口采纳。两次请求均返回 200。完整检查的 `reviewed_refs` 包含 101 个 ID 时，返回 `SCHEMA_INVALID`（`maxItems=100，实际长度=101`）；截成 100 个 ID 后，响应 Schema 合法，但 `prewrite.validate_result` 返回 `PREWRITE_COVERAGE_REQUIRED`。因此既不能完整提交检查，也不能靠省略条目通过。

同一上限也影响“1 条需求 + 50 条规则 + 50 条验收”的 101 个规范条目。将该不合法检查强行送入内部编排的结果只用于定位，不计为正常成功路径。

根因：`requirements-agent-codex-kit-v1.1/examples/runtime_response.schema.json` 的 `reviewResult.reviewed_refs.maxItems=100`，与 `app/prewrite.py:validate_result` 的全部本期规范条目覆盖要求冲突。`app/workflow.py` 在真实成文检查路径依次执行这两项校验。

修复验收：覆盖 100/101 个规范条目边界及需求、规则、验收混合；保持逐项真实审查和完整覆盖，不能通过删引用、伪造审查或跳过检查解决。另一个下游功能清单表也有 100 个引用上限，应在解除上游阻塞时一并处理；本轮没有将它重复算成独立正常路径缺陷。

### F2：各自合法的长需求和长回答，拼接后导致整份 PRD 失败

**影响：用户已经保存的内容不能成文，重新点击会重复失败。**

实际 HTTP 接口分别保存 4000 字符需求正文和 4000 字符问题回答，均返回 200。冻结检查响应通过 Schema 校验，检查状态为 `passed`。之后调用实际 `POST /api/projects/{pid}/documents/prd/local-review`，返回 400 / `SCHEMA_INVALID`。

`app/prd.py` 把问题、回答、回答来源、关联条目当前快照与来源说明拼成一个 narrative 块，本例为 8111 字符；该块上限是 8000。错误显示为 `maxLength=200`，是 `oneOf` 多分支错误挑选造成的误导，不代表合法 narrative 的真实上限为 200。

失败后项目及 records 与请求前完全一致。没有截断原文或损坏已保存内容。

修复验收：分别合法的正文、回答和引用说明组合后仍可完整生成；按块/章节拆分保留全部原文、引用与审计关系。错误提示应定位实际块类型。不要仅删除回答审计或静默截断文本。

### F3：积累 100 条含限制说明的历史响应后，历史附录超过章节容量

**影响：项目长期使用后，即使当前需求很小，也可能无法再次生成 PRD。** 不是每 100 次点击必现；触发条件是至少 100 条历史响应各自含非空 `limitations`。

对同一隔离项目构造 100 个分别经 `validate_response` 验证的冻结 review 响应，每个仅包含一条合成历史限制；通过真实 `response_application.apply_response` 逐个应用，形成 100 条助手历史。当前检查合法。调用本机成文失败：`sections[6].blocks maxItems=100，实际长度=101`。

根因：`app/prd.py:historical_notes` 读取这些真实历史，编排“历史分析提示（非当前事实）”时加入 1 个说明块，再加入 100 个历史块，但该章节没有按容量分组。99 条历史限制的对照成功。

失败后项目与 records 均未改变。修复验收应覆盖 99/100/101 条历史提示，完整保留历史身份，并保证历史附录分组后仍不会混入当前业务事实。

### F4：100 个非阻断问题关联一条需求时，风险表的引用数量超限

**影响：允许保留未决事项的评审稿也会因风险表编排而失败。**

每个问题单独通过 `Question` Schema 校验，再使用真实 `understanding.save_questions` 逐个保存；100 个不同问题均为 `blocking=False`，关联同一条需求。冻结检查响应合法。99 个问题的成文成功，100 个问题失败，错误为风险表 `ref_ids maxItems=100，实际长度=101`。

根因：`app/prd_sections.py:risk_register_blocks` 将全部问题 ID 与关联需求 ID 聚合到单张表，去重后是 100 + 1 个引用；`app/document_schema.py` 限制单张表最多 100 个引用。还没有触及风险表自身 200 行上限，就已经失败。

这项通过真实内部保存方法证明了合法累积状态，没有声称在浏览器中创建了 100 个问题。失败时项目和 records 不变。修复验收应按引用数和行数共同拆表，保证每行的风险、影响、处理建议与原问题关系不丢失。

### F5：角色交接文件遗漏结构化详细定义，并把已知内容写成“未指定”

**影响：开发者仅阅读角色文档时，可能将已确认的产品规则误认成需要技术设计补充的事项。**

合法详细需求包含四个标记：

- 姓名为 1 至 27 个字符，超限时不提交。
- 保存失败时保留输入，并提示“联系人未更新，请重试”。
- 仅同站点成员可见联系人姓名。
- 保存过程中重复点击只处理同一次提交。

实际普通 Word、Markdown、reader，以及正式交接中的 `PRD.md`、`PRD.content.json`、`delivery_scope.json`、`requirements-exchange.json` 都包含这四项；`requirements.md`、`frontend_spec.md`、`backend_spec.md` 均不包含。前端文档有 5 处、后端文档有 4 处“未指定，需技术设计时核对”，且角色文档没有直接指向完整详细定义。

根因：`app/exports.py:handoff_files` 共同正文只投影 `statement`，角色行为只读取旧式 `behavior`，没有读取 `detail_contract`。README 确实说明了机器范围文件，所以不能把该问题描述为整个交接包丢失需求。

复现走过真实本机生成、普通导出、checkpoint、文档核对、正式确认和交接 ZIP。正式确认前 `gate=[]`，未绕过门禁，未直接伪造 baseline。原始详细需求和语义核对结果为合成/冻结输入。

修复验收：同一基线的角色交接文件正确呈现详细定义；若定位为摘要，必须清楚说明并链接完整内容，不能把已有定义标为未指定。完整旧式 `behavior` 的正向对照已经通过，说明这是新旧结构投影不统一的问题。

### F6：正式交接包的 PRD Markdown 丢失风险表行

**影响：评审时可见的风险提醒，在正式交接文本中不可见。**

通过真实 `prewrite.apply_result` 添加一个非阻断警告：“AI建议，待核对：联系人保存失败后重新提交的提示是否清楚。”检查状态 `passed`、阻断数为 0。普通 Word、Markdown、reader 及正式包的 `PRD.content.json` 均有提醒。经过正式确认后，ZIP 的 `PRD.md` 风险章却只剩“风险点与待确认”标题，没有该行。

根因：`app/exports.py:handoff_files` 直接拼接 block 的 `text`；表格内容存储在行数据中。普通 `document_files` 使用 reader 节点与 `table_markdown`，所以普通导出能保留表行。

此例丢失的是非阻断评审提醒，底层结构化内容仍在；不能据此夸大为已证实关键业务数据整体损坏。修复应统一普通下载与交接 Markdown 的渲染路径，并验证所有表行，而不只是章节标题存在。

### F7：已复核消解的问题，在交接文件中重新成为“未决事项”

**影响：工作台、正式 PRD 与交接追溯文件给出相互矛盾的状态，接收方可能重复澄清已处理的问题。**

通过真实成文检查生命周期提出关于 Unicode 码点或字素簇算法的技术追问，保存合成用户异议，再用合法冻结复核结果接受异议。没有直接写入 `prewrite_resolution`；它由真实处理逻辑产生。

交接前，问题保留历史 `status=open`、`answer=null`，但 `resolution_basis=reviewed_dispute`、`resolution_current=true`、`question_open=false`；普通 Word/Markdown 不再把它列为未决。正式确认 `gate=[]` 后，导出包的 `open_questions.md` 和 `traceability.json.open_question_ids` 又包含该问题，同包 `PRD.md` 却没有。

根因：`app/exports.py:handoff_files` 仅判断原始 `status != answered`，未使用 `app/product_flow.py:question_open` 与 `app/prewrite.py:question_resolution_current` 的当前有效状态逻辑。

修复验收：同一 baseline 中所有产物对当前未决事项一致；仍保留历史追问与消解依据，不得为了导出一致而虚构用户回答。

### F8：本机成文的同步工作阻塞服务事件循环

**影响：需求规模增大时，生成期间其他 API 也无法及时执行，用户可能感到整个工作台停住。**

实际 `app/main.py` 的本机预览和成文路由是 `async def`，却直接执行同步的 preview/generate。本轮通过 `httpx.ASGITransport` 调用实际应用工厂和路由，不启动监听服务：

| 场景 | 生成结果 | 另一个查询获得执行机会的延迟 |
| --- | --- | --- |
| 1 条需求，显式注入 0.35 秒同步处理延迟 | HTTP 200 | 约 0.388 秒，生成结束后才执行 |
| 同一输入与延迟，仅内存路由改用线程作为对照 | HTTP 200 | 约 0.003 秒，可在生成结束前执行 |
| 99 条合法需求，无延迟注入、无模型调用 | HTTP 200，实际生成约 5.77 秒 | 约 5.83 秒，生成结束后才执行 |

这不是实机浏览器计时、网络 SLA 或 Windows 性能结论；它直接证明当前 ASGI 路由的同步执行阻塞。内存线程处理仅用于证明根因，没有改产品源码。

修复验收：将耗时工作移出事件循环，同时保留事务、并发任务、版本和幂等约束；同一工作台生成文档时，状态/列表等轻量请求应能及时处理。线程对照不能代替正式并发回归。
