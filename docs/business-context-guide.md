# 工程上下文使用说明

工程上下文包帮助需求 Agent 理解获准读取的代码快照：业务职责、架构、数据流、数据模型、接口、依赖和实现约束。它描述导出时可追溯的现状，不自动决定本期新需求，也不证明线上部署版本。

1. 在获准读取的源码目录使用 `export-business-context` Skill，指定目标系统和输出位置。Skill 只读导出单个 `business-context.json`，为陈述附上文件、行号、哈希和来源类型，并记录快照版本、覆盖范围、未知与冲突。不要放入密钥、原始数据或无关文件。
2. 在“项目资料”中选择“导入工程上下文”。新包导入成功后默认启用全部模块，可直接查看工程总览和按维度分组的陈述及出处。若导入的是已有版本，先看资料卡片是否显示“未启用”，需要时打开该版本并启用。
3. 如本次只涉及部分模块，展开“调整参考范围”，缩小模块并保存；依赖模块会一并纳入分析。旧版切换后保留原模块选择，可再次启用。停用或排除的版本不参与分析。

有出处的代码或配置观察可直接用于**该快照**的现状描述；文档陈述必须说明文档来源。推断、冲突和未知分别保留原身份，不能写成已验证事实。静态代码观察不等于运行验证；部署环境和目标版本须另行核对。本期业务规则仍由需求流程决定，不能由包自动采纳。

## MRD 与 PRD 的使用

工程上下文用于解释现有链路、对象、数据流与改动影响；本次明确提出的新功能仍会建立需求候选，字段或失败提示不完整时继续澄清，不会因为当前代码尚未支持就否定需求。

新生成的 v4 MRD 正文围绕现状、使用者、问题价值及范围，精确产品条款放入附录；PRD 将功能需求、业务规则和验收条件分别归位，保留操作流程、数据、权限和异常结果。解释正文必须引用当前可用依据，历史讨论和组装过程不进入阅读正文。

已生成文档不会被后台改写。旧项目需按原流程更新 MRD/PRD 才能看到新版生成效果；新导入版本改变了参考事实时，也需要重新核对受影响的范围和文档。市场数据、量化收益、线上状态等无法从代码推出的信息，仍需相应资料。

2026-09-29 的合成样文已核对成功、权限失败、事务回滚和网络不确定性；仍存在少量解释复述，不能把单一样文结果视作全部业务的文档质量保证。
