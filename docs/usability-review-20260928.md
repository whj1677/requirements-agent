## DeepSeek Harness 评估与后续边界

用户已明确指现有 `ui-test-agent` 使用的 DeepSeek Harness。2026-09-28 只读核对当前 `workbench/server/backend/harness-manager.mjs`、`harness-session.mjs` 及其进程控制入口，未修改该工程，也未调用其模型。

当前适配确有同一会话中的 `read_context → write_draft → self_test → review_candidate → submit_candidate` 反馈修订路径。这适合有明确输入、工具与验收的子任务。当前接入代码仍把 `provider_requests`、`provider_usage` 记为 null；没有找到由该适配层实现或验证的跨会话模型恢复、需求材料分页检索与上下文压缩保证。它还包含测试工程自己的总时长/工具次数限制，不能原样迁移后宣称需求 Agent 仍无限预算。这不是对 Harness 本身能力的全面否定。

判断：本轮不替换需求 Agent 底层。已复现的“分析不动”根因是旧预算误计图片传输内容及不可见失败；旧问题已修复，残余真实模型保真失败也不能直接归因于上下文不足。引入另一套运行时会增加进程、工具边界、取消和证据接入成本，尚无同输入对照证明收益。

后续仅在明确上下文失败样本后做有限对照：冻结相同材料与预期，先实现按来源 ID/位置读取片段、单章节候选和程序合并校验，再比较现有调用器与 DSH 工具循环。负责人继续控制事实来源、版本、授权、采纳、基线及导出。验收需同时检查长材料覆盖、矛盾保留、取消恢复和真实用量；不能用更大输出上限或更多 Agent 数量代替验证。

修复仅将资料抽屉关闭按钮和 Escape 改为直接收起。第一步仍挂载，资料文字和 URL 仍由 Workspace 持有，重新打开可继续编辑；真正切换项目仍由原守卫保护。只有资料、没有文字时显示“已保存资料范围，未填写文字”，不再笼统显示“输入已保存”。不通过禁止仅资料分析掩盖问题。
