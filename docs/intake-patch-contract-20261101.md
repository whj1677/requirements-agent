## 根因与最小修改

第一次实际补丁把验收和问题的数组槽写成 `{"items":[...]}`。原 Schema 明确要求数组，原接收端正确拒收。第二次实际补丁已用数组，却为 8 条新增验收编造 `target_ref: C1…C8`；原项目没有已有条目，补丁静态 Schema 仅限制编号格式，而正常业务接收要求真实、当前、直接关联的已有验收，因此正确拒收。

`intake-grounding-patch-2` 将补丁契约与既有可编辑目录对齐：按候选行 `row_key` 精确匹配本轮 `current_rows`，验收槽只允许该行 `editable_acceptance_refs` 中的已有目标。没有匹配行或目录为空时，禁止返回 `target_ref`；新增验收必须省略此字段，不生成新编号，不把其他行或只读修订当编辑目标。没有本地删引用、猜目标或业务内容改写。

补丁输入的每槽明确 `value_type`，验收槽另列真实白名单；提示要求数组直接写 `[...]`，禁止 `{"items":[...]}` 外壳。未加入宽泛格式归一化，原违规回包继续拒收。Provider 仅扩展应用可信首条系统任务头的已知协议白名单；用户资料中的同文伪头不获得归一化权限。

来源 challenge-2、已答 coverage-1、paired-7、最多两轮纠正、修后两项完整复核及现有额度均不变。业务接收端原有真实目标、直接关联、只读修订和来源校验未修改。Schema 更明确并不保证真实模型一定遵守，仍需真实流程复验。
