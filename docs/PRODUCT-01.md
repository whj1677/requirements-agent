## 明确改变的旧产品规则

- 五步自由动作改为六步有前提的主流程；可看历史和说明，但直接 API/诊断不绕过执行前提。
- MRD 从可选变为默认交付，与 PRD 共用需求版本，但章节关注点不同；调整范围需人工说明。
- 正文去技术噪声不再隐藏需求编号。保留业务编号与版本，去掉运行 ID、完整历史问答和内部字段。
- 业务页面定位需求草图，静态表达足够时不强制 CRUD；第四步核对不代表专业 UI 批准。
- 未决问题按实际影响阶段处理；非本期问题须有明确移出范围的理由。旧版“所有未答一律阻止任何下载”需按新评审/交付条件区分，不能把未知改成不适用。
- 历史结果不补造阶段核对；提供基于现有数据的补核对。旧失败事实不重写。

## 可检查产品样板（设计与验收预期，非产品生成结果）

六步：提供现状与诉求 → 核对现状、价值与改动范围 → 澄清流程与规则 → 核对功能草图 → 评审 MRD 与 PRD → 确认与交接。
工作台保留左侧项目、中央任务区和右侧材料/助手；中央只显示当前步骤的一项主要任务、结果、缺失条件与下一步。可按需求编号定位。

样板A：公开现有问题列表，新增一项局部列表辅助操作；原页面作为静态现状参考，只绘制新增区域及路径说明。实际截图来源与具体预置诉求在本机验收材料中冻结后记录，不将设计样板计为真实生成。
样板B：既有联系人列表新增备注字段；原查询和只读权限保持，备注是否必填、保存反馈和边界来自预置合成材料。独立业务场景，不含问题列表或电价规则。

MRD 目标目录：业务背景与依据、目标用户及价值、范围/优先级与影响、逐需求功能概述及变更类型、风险/依赖/验证计划。缺量化依据就明确暂无量化资料。
PRD 目标目录：文档范围及需求版本、现状/角色/流程、逐需求改动及草图、业务数据/规则/权限、边界/异常、验收与回归关注点。两者复用同一原文与编号，不从模板继承字段约束或公司信息。

样板身份：`REQ-<现有唯一ID>` 的标题可变，内容 v1→v2 不改号；`AC-…` 验收点和 `TC-…` 测试用例保持不同对象类型，关系显式写 `verifies`，允许多对多。关联存在不等于执行通过。

## 编号、版本与兼容方案

沿用既有程序分配的条目 ID，需求继续使用 REQ 编号，不做历史全量改号。独立内容版本与项目底稿版本分开。取消/恢复只改状态，内容未变不增加内容版本。
命名空间记录来源项目的稳定唯一身份，跨项目迁移保留最初来源；独立副本保留来源身份，因此重复导入可识别。相同身份+相同版本但内容哈希不同必须冲突；不偷偷改号。同一常用编号在本机跨项目发现不同原始身份也显式冲突。
旧对象没有独立版本时按 legacy v1 解释，不改写历史快照；首次真实内容编辑产生 v2，并保留原文记录。导出记录此解释边界。
不新增重复事实库：需求仍存在当前 items，历史依托 revisions/records，导出是其版本化投影。关系引用对象类型、编号、版本与基线，未来平台通过独立消费者校验/合并，不臆造远程 API。

## 验收与停止

验收映射用户15项场景；必须以实际路径/产物与内容检查为证，不以测试数量替代产品判定。工程、合成模型、真实模型、真实页面和真人批准分别报告。
本轮最终交付独立可运行版本、双文档/草图/机器导出、操作入口、命令与退出码、本地和远端版本以及剩余限制。达到目标后交用户做最终体验和内容验收，不自行宣称发布或部署。

### 真实调用与失败

本轮唯一 `call_id` 去重后 **26次请求，11次修复关联**：vision 3、ingest 5、clarify 3、ui 11、prd 4。响应校验为 accepted 13、SCHEMA_INVALID 11、REFERENCE_INVALID 2；accepted 仅指结构/引用接受，不表示业务验收。多份一致性副本中的继承账本不重复计数。

供应商可取得usage合计：prompt_tokens 495544，completion_tokens 86278，total_tokens 581822；逐请求耗时合计约320.952秒（不是操作全程耗时）。单次max_tokens全部16000，finish_reason无length；费用未知。原pilot-01、餐饮15次与旧LIVE验证账本不变。

两次草图任务耗尽各自3次修复额度后失败，原输出仍保留；一次澄清重复提出已有问题、未补齐行为，另次明确指令后才完成。后续静态草图和布局候选经修复成功。最终两份文档v2各使用1次请求保存，未通过修改返回JSON冒充模型成功。由此不能宣称模型一次生成可靠率已验证。
