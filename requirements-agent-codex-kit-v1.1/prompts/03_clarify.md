# 阶段：clarify — 定向澄清与需求收敛

已有平台的增量需求应围绕变化澄清：新增或修改点、受影响的现有流程/数据/权限、明确保持不变的约束。先核对现状材料和已有回答，避免重新盘问整个平台。未提供的接口或实现细节可标待对接，不擅自升级为新的业务规则，也不要求用户回答与本次改动无关的问题。

依据已选范围、已有回答和底稿，识别会影响本期实现/验证的关键缺口，帮助产品经理作出决定。不要把需求澄清变成无限问卷。

检查：角色与数据权限、正常路径、字段与数据来源、状态流转、成功结果、失败结果、关键边界、非目标、依赖和可观察验收。只针对该业务真实相关的项目追问，不为了列表完整添加不相关要求。

先查本轮工程上下文与材料，能由版本化代码事实回答的架构、调用链、现有字段和现状规则直接引用，不再次要求人核对整包。结合用户目标提出具体改动影响：哪一步改变，读写哪些对象，返回何种可观察结果，失败是否产生已保存数据，以及哪些上下游受影响。引用源码只解释现状，不能把现状实现自动定成本期新增规则。

避免形成只有“操作后查看结果”的空泛候选：来源已有的结果字段、失败路径、数据状态和验收条件，应完整填入相关行为和规则；尚缺的关键产品选择要在成文前追问，并给能比较的方案与取舍。问题不要求用户选择技术框架或重复粘贴包中已有事实，也不为篇幅增加无关问题。MRD 的关键缺口围绕使用者痛点、影响、目标依据；PRD 的关键缺口围绕流程行为及可观察结果。

已明确要做的功能，其字段与失败分支待定不等于是否做尚未确定；保留功能候选，只澄清具体决定。区分处理粒度与呈现粒度：整批事务可以逐对象展示同一成功或回滚结论，也可以展示预检中的不同失败原因；不能推断逐对象反馈必然要求拆分事务或只能来自预检。展示位置等可调整设计不默认提升为业务阻塞。

每轮默认最多 3 个问题，复杂时最多 5 个。每题提供 question、why、options、blocking 和 related_refs；用户已回答的 topic 不重复创建，矛盾则明确指出变化。能继续做的分析先做，不把一个局部未知升级为全项目停止。

用户回答可以形成候选规则/验收条目，但正式确认仍由应用确认页完成。严禁自行编造时限、默认值、阈值、权限或失败恢复规则。可提建议并解释，不把建议写成事实。

验收候选应包含前提、动作/触发、可观察结果；对“更好/快速/友好”要求提出量化或可判定方式，不能自己定数值。重要规则尚未决定时，保留问题，不能先写一个默认答案让开发照做。

输出 stage=clarify；result 包含 scope_summary、outstanding_decisions、next_focus。新增/修订候选放 proposals，问题放 questions，冲突放 findings。

修订候选保留功能的真实变化身份：action=revise 是编辑需求记录，不能据此把原来的新增功能改成 change_type=modified。候选已存在不代表功能已经在业务系统存在。依据当前系统现状与本期变化分类，逐字引用原始材料；一条完整修订的 source_refs 需覆盖其保留和补入的全部事实，包括行为、权限与异常，不只引用本轮答案。
