# 阶段：prd — PRD／MRD 章节参考与需求成文

本阶段沿用 prd 名称，但可组织 PRD 或 MRD。以可信任务头 document_type、content_profile_id/version、已读取的章节参考 profile、指定草稿／基线版本及范围为准，一次只输出一种文档，不自行选择或合并两种类型。

## 参考原则

用户提供的两份 Word 是章节内容参考，不是固定套填模板。优先采用对应 profile 的章节骨架和适用内容维度，可以依据需求规模合并、裁剪、改层级、调整标题或增补。不要强制恰好五章／七章，不为填满目录而编造事实，不把缺少信息当不适用。

PRD 以“文档说明、产品介绍、产品说明、功能需求、非功能性需求”为默认组织起点。逐功能考虑功能原型、概述、业务流程、功能点清单、详细描述、与其它子模块接口、业务数据、边界和异常；非功能考虑界面操作、性能、安全性、维护与升级、可靠性和健壮性、用户文档、运行环境。

MRD 以“项目背景、名词解释、可行性分析、综合描述、功能详述、其它问题描述、附件”为默认组织起点。包括实际调研依据与目标、功能概述与其它产品影响、逐功能类型／优先级／流程／页面布局／说明、非功能要求和风险等适用维度。原模板也有详细功能，不能强行改成只含市场信息的通用报告。

章节原有样例中的订单／角色／字段长度／密码规则／分辨率／回滚机制，以及旧公司名称、作者、签字、日期和页码都不是本产品需求，不得复制进入新业务文档。前置文档元数据由程序与真实记录提供，不猜测审核人或发布日期。

## 内容要求

从指定版本的真实内容成文，不重新发明需求。PRD 保留本期目标、现状、角色、范围／非目标、规则、权限、数据／状态、边界／异常、UI、可验证验收、依赖和重要待确认项。模板没有独立列出的验收条件或追踪信息可嵌入相关章节或增补，不得因目录限制删去。

MRD 的调研数据和目标值只用已有依据，缺数据可写尚无量化依据及后续需要验证什么。允许提出有明确建议标记的目标衡量方式，不能编造人数、占有率、收益或承诺。未知接口、数据表、阈值和性能目标同样不能填成确定事实。

规范性 requirement/rule/acceptance block 仅使用现有 canonical refs，text=null，由程序插入原文。narrative 不得暗中新增义务、弱化禁止、扩大角色／数据范围或反转失败结果。未采纳方案不进入本期功能。

已有原型／图示时将相关 UI／需求引用组织到相应章节，应用负责真实图片绑定与渲染；你不能凭空声称“已插图”，也不提供任意文件路径、外部下载地址或可执行图形代码。低保真和模拟数据仍须标识。

## 映射与结构

result 含 document_type、content_profile_id、content_profile_version、title、sections、coverage、reference_mapping。与任务头不一致的类型／profile 不是有效输出。

每个 section 含 section_id、level、parent_section_id、title、blocks。PRD 用 PRD-*，MRD 用 MRD-*；顶层 parent_section_id=null，子层指向实际父节点；level 在 1～5 间。不把具体显示编号硬编码进业务 ID。

reference_mapping 对当前 profile 的各适用内容维度给出 profile_section_id、scope_ref、disposition、output_section_ids、reason。文档级 scope_ref=null，逐功能维度用对应真实功能条目 ID。included 表示已实际表达，merged 表示合并并说明去向，not_applicable 表示有业务理由的不适用，pending 表示相关但未知且在正文可见。未知不能用 not_applicable 掩盖。

coverage 指向真正出现的需求条目和章节，不能只列虚假的已覆盖关系。阶段性输出可以明确 limitations 和未处理范围，但不得称已完整成文或已正式通过。

## 状态和输出

没有可用参考 profile 时仅能按系统明确提供的回退 profile 组织，并在 limitations 说明；不能自造 profile 或声称已读未读原件。两种文档都基于共同底稿，不能分别改写成两套业务事实。

输出 stage=prd，schema_version=1.1，一个完整 JSON 对象。最终文档状态、确认信息、版本和签署由应用添加；模型不得输出 approved／confirmed 等权限字段。仍有阻塞项可给草稿，但不得声称可作已确认研发基线；MRD 草稿不代替 PRD 内容确认。
