# 阶段：prd — 有来源的 MRD/PRD 文档计划 v3

严格按可信任务头中的 `plan_contract` 和 `schema` 输出完整 JSON。只有计划和受控解释由你生成；章节标题、已选规范原文、行为字段、开放问题、来源与限制由程序按当前快照组装。`example` 只演示结构，不是项目答案。旧 v2 对象仅用于已有历史记录和离线兼容。

MRD 解释问题、受影响角色、现有处理方式、需求依据、目标、衡量方法与业务影响。没有真实频率、收益或市场数据时，不编造数字。PRD 解释已决定的使用场景、入口、正常和替代流程、状态、数据、权限、异常结果和可观察验收。依据不足的流程或规则回到待确认候选，不能写成确定要求。两类文档应履行不同职责，避免把同一组正文仅换章节位置。

每个 `explanations` 项须用 `evidence_refs` 精确列出本段依赖的已核对 `context_refs`、本期已选 `normative_refs` 或用户已确认的 `business_claim_refs`，三组至少一组非空。引用只能来自各自的当前白名单。业务包里未确认的代码观察、推断、冲突和未知可帮助提问，不得成为正式正文事实。解释可组织已知关系，不能新增数值、状态转换、权限、默认行为、业务承诺或改变已选规范的适用条件。不能用一条宽泛背景引用掩护无依据结论。

`context_refs` 只能引用当前已核对产品上下文；`normative_refs` 只能引用本期已选规范；`discussion_refs` 只能引用讨论白名单。规范由程序回填原文，候选始终留在独立审计附录。至少引用一项当前事实或条目；省略空章节。尽量安排所有相关已核对上下文和已选规范，遗漏由程序补列。不能输出自定义章节标题、来源说明、限制说明或讨论过程。

输出是待人工核对的文档草稿。语义审查及产品经理人工评审仍需检查解释是否扩大、弱化或反转规范，以及业务场景是否完整；结构与引用检查本身不能证明语义保真。只返回 JSON 对象，不附加解释。
