# Word 文档输出：PRD / MRD 章节内容参考规范

版本：1.1｜日期：2026-09-23｜本次用户变更：输出的 Word 文件参考所提供的两份模板，**主要参考章节内容，不是固定格式套填**。

本规范与任务书、运行时提示词、数据契约和验收项配套。此前“未提供原模板”“只用内置通用结构”“原模板适配以后再做”的描述已由本次更新替代。应用实现、Word 导出效果及真实模型效果仍需 Codex 实测，本文件不是测试通过记录。

## 1. 两份原始参考文件及使用边界

| 参考 ID | 包内原文件 | 参考用途 |
|---|---|---|
| REF-PRD | `references/产品需求文档PRD模板(1).docx` | PRD 的章节组织、逐功能描述维度、角色和业务数据等内容表达 |
| REF-MRD | `references/百度产品需求管理文档（MRD）模板(1).docx` | MRD 的背景、调研依据、预期目标、影响、功能/非功能和风险等内容维度 |

原件仅作参考，保留原始字节；哈希及机器可读章节映射见 `references/content_profiles.json`。Codex 先核对文件与映射，再实现导出。不得拿其它网上模板替换这两份材料，也不得只看文件名就宣称已适配。

**“参考模板”的含义：**以原章节作为默认组织起点和内容检查维度，依据真实需求规模合理增补、合并、裁剪、调整层级。不是强制标题逐字一致、章数固定、每节必填，更不是复制原文档后挨个替换占位符。

参考的是“应考虑哪些内容”，不是模板示例中“这个项目已经决定了什么”。产品需求、人员、规则和确认信息只能来自当前项目材料、底稿与真实确认记录。

## 2. 文档类型与流程

应用须具备 PRD 与 MRD 两种 Word 输出能力。**默认生成 PRD；用户可以按需选择 MRD 或两者。支持两种文档不等于每次必须写两份，也不要求先完成 MRD 才能写 PRD。**本次不引入新的独立 MRD Agent 或额外审批系统。

PRD 仍承担已有的研发需求评审和内容确认主流程。只做探索或立项材料时可以单独生成 MRD 草稿；这不会自动获得正式研发交接资格。两份文档选择同一项目、同一底稿 revision 或同一已确认 baseline，共享业务事实，不让用户重复澄清。

PRD 参考 REF-PRD 为主，MRD 参考 REF-MRD 为主。允许把另一份参考中的相关维度整合进当前文档，但不要把两套目录硬拼成一份冗长文档。MRD 原模板也含详细功能、流程与页面布局，不能机械认定“MRD 只能谈市场、不许写功能”。

PRD.md 与 PRD.docx 从同一 PRD 内容对象生成；MRD.md 与 MRD.docx 从同一 MRD 内容对象生成。PRD 与 MRD 内容侧重点可以不同，但同一规则、角色、范围、数据和目标不得矛盾。

## 3. PRD：从原模板提取的默认章节骨架

以下标题和细分维度来自 REF-PRD 的目录及正文，不是新创造的业务要求。目录中的“前言”没有对应的独立正文内容，可作为可选前置说明，不将其设为强制新增章节。原文件目录页码和正文页码不直接复用。

```text
文档基本信息、修订历史、目录（前置管理信息）
第一章 文档说明
  1.1 文档的目的
  1.2 参考文献
  1.3 产品命名规则
第二章 产品介绍
  2.1 产品概要说明
  2.2 产品用户定位
  2.3 产品中的角色
第三章 产品说明
  3.1 产品信息结构图
  3.2 产品功能结构图
  3.3 用户使用流程图
第四章 功能需求
  4.x 功能点（按本期功能重复）
    4.x.1 功能原型
    4.x.2 功能概述
    4.x.3 功能业务流程图
    4.x.4 功能点清单
    4.x.5 功能详细描述
    4.x.6 与其他子模块的接口
    4.x.7 业务数据描述
    4.x.8 边界值处理
    4.x.9 异常处理
第五章 非功能性需求
  5.1 界面操作需求
  5.2 性能需求
  5.3 安全性需求
  5.4 维护与升级
  5.5 可靠性和健壮性
  5.6 用户文档需求
  5.7 运行环境
```

### 3.1 如何用这些维度

产品介绍可包含本项目背景、现状、用户痛点及目标；产品中的角色可用“角色名称／职责描述／使用的功能／权限等级或范围”表述，参考的是表达维度，不沿用模板示例的管理员、渠道经理、运营角色或数字等级。

信息结构、功能结构、使用流程是不同表达角度。小需求可以合并图示或用简短步骤／关系表替代复杂图，记录对应关系即可，不能为了图多而编造模块。产品已有页面线框时，PRD 的“功能原型”应嵌入相应实际线框图或受控图片，并注明 UI 版本、功能关联及“低保真／模拟”；不能只输出一段未渲染代码来冒充图。

“与其他子模块的接口”首先描述业务依赖与交互要求，不因为模板有该节就凭空决定 HTTP 路径、数据表或事务实现。“业务数据描述”考虑对象、字段含义、来源和已知约束；未知长度、精度、默认值和角色权限要明确待确认。

## 4. MRD：从原模板提取的默认章节骨架

以下结构来自 REF-MRD 的目录与正文。保留原材料中的“项目背景／综合描述／功能详述”等术语，不用通用市场报告框架静默替换。

```text
MRD 基本信息、重要性、紧迫性、审核／拟制／提交信息、
需求变更控制时间点、修改记录、目录（前置管理信息）
1 项目背景
2 名词解释
3 可行性分析
  3.1 前期调研信息和数据
  3.2 项目预期目标
4 综合描述
  4.1 功能概述
  4.2 对其它产品的影响
5 功能详述
  5.1 功能需求
    5.1.x 功能点（按本期功能重复）
      5.1.x.1 功能点类型和优先级
      5.1.x.2 流程图
      5.1.x.3 页面布局
      5.1.x.4 功能点描述
  5.2 非功能需求
6 其它问题描述
7 附件
```

### 4.1 需要保留的内容含义

“前期调研信息和数据”写实际提供或授权取得的调研依据，保留来源和局限。没有量化研究不能编造市场规模、访谈人数、增长率或收益；可以写“尚无量化调研依据”，说明当前判断建立在哪些实际材料上。

“项目预期目标”可以建议可量化方式，但数值尚未决定时保持待确认，不为填表伪造指标。功能点类型参考原文的“新增、旧有功能升级、Bugfix”；优先级参考“高、中、低”，在当前团队另有已明确规则时使用其规则并说明映射，不能沿用样例优先级当决定。

“对其它产品的影响”涵盖相关假设、依赖及外部系统接口关系。“其它问题描述”考虑上线风险、应对措施和对其它部门的影响，不以“其它”之名省掉已知重要风险。

非功能需求的原文维度包括性能、可维护性、可靠性、安全性、安装性等。它们是检查维度，不是所有项目必须追加的范围或指标；安全性等词的项目含义需要结合当前业务澄清，不能静默改写原材料的定义。

原 MRD 明确允许裁剪部分无关项，例如名词解释、简单流程图、缺少页面模板时的页面布局及无关附件等；本项目也允许相应的内容裁剪，但“没问清楚”不能被当成“不适用”。

## 5. 在参考结构之外补充的本项目要求

以下是当前 Agent 的工程交付要求，**不是声称两份原模板原文已有这些完整章节**：

- 本期范围与非目标、已采纳／未采纳方案边界。
- 可验证的验收条件及 REQ／RULE／AC 关联。
- 事实、建议、假设、待确认项和确认范围的区分。
- 底稿／内容版本、来源引用、UI 关联、待决事项与变更影响。

优先把它们放入对应章节（例如验收条件放在逐功能描述之后，待确认项放在相关功能及文末汇总），必要时新增“验收条件”“待确认事项”等节或附录。不能因为原目录没有标题就删掉这些内容，也不应为每项机械添加一章。

## 6. 裁剪、合并和待确认的规则

内部保存“参考维度 → 实际输出章节”的映射；用户看简洁目录和有必要的裁剪摘要即可，不要求产品经理填写技术映射表。

| disposition | 含义 | 处理要求 |
|---|---|---|
| included | 对应内容已表达 | 关联实际章节 ID；能定位内容而非只存在空标题 |
| merged | 合并到其它章节表达 | 关联实际章节 ID，并记录合并去向／理由 |
| not_applicable | 当前范围确实不适用 | 记录业务理由，不生成无意义空章节 |
| pending | 该内容相关但尚不明确 | 在相关章节或待确认汇总中明确未知及影响，不能静默省略 |

不是要求成文结果恰好五章或七章，也不是要求标题顺序完全不变。验收重点是适用内容已表达、裁剪有依据、重要未知可见、事实无污染、与底稿一致。

对逐功能维度，映射以功能条目作为实例范围；一个功能不适用不代表所有功能均不适用。功能原型、业务数据、边界和异常的关联不得只用一个“已覆盖”概括全部功能。

例如一个仅改列表展示的小需求，可以把信息结构、功能结构和操作路径合并为“页面与交互”，但角色可见性尚未确定时要保留待确认问题，不能因不想追问而把安全性／权限标为不适用。

## 7. 不允许继承的模板内容

不得将模板示例中的订单审核、订单撤销、产品管理场景、角色、用户名和密码长度、字段长度、800×600 显示要求、原子回滚处理等直接转为本产品规则。它们只说明模板里曾展示过某种写法。若本项目的独立实际材料恰好明确相同规则，可按该实际来源引用；不因文字与样例相同就机械判错，禁止的是无依据继承。

不得在新文档冒用原公司的名称、版权声明、样例作者、审核签名、V2.10、2016 年日期、占位符、“第 X 页共 2 页”等旧页码。原始参考文件仍原样保存，限制针对新生成的业务文档。

也不要求复制原字体、色彩、页边距、表格宽度、封面、图表配色或截图。无需复刻原样式，但新生成 Word 应有清晰层级、可读表格、正确分页和版本标识。模板中的原型链接不自动变成访问授权，也不能替换本项目原型。

## 8. Codex 的实现要求

采用“结构化业务底稿 → 按内容参考 profile 组织文档内容 → 同一内容对象渲染 MD／DOCX”的链路。优先新建干净的 DOCX，而不是无差别复制原 Word 内容。可复用必要基础样式，但新文档不得留下原业务、旧图、旧页码或样例审核记录。

`references/content_profiles.json` 是本包根据原材料整理的参考配置，不是新业务事实，也不是用户必填表单。业务素材的 `purpose=content_reference` / `applies_to=reference` 与本期需求源分离，模板正文不能自动写成 REQ／RULE。

内部仍复用 `stage=prd` 文档组织阶段，以 `result.document_type=prd|mrd` 指明类型；这是兼容既有阶段名称，不要求另建 MRD Agent。按当前类型只装配该 profile 及必要项目内容，避免把两份模板全文和无关样例送入每一轮。

模型输出章节结构和引用；程序校验 profile、层级、功能范围、映射、引用及版本，插入规范性规则原文，再渲染两种格式。模型不能通过选择章节或“已裁剪”标记删除关键规范。图片由应用根据 UI／材料来源绑定，禁止让模型随意提供本地路径或外部图片地址。

默认导出：`PRD.md`、`PRD.docx`；选择 MRD 时对应 `MRD.md`、`MRD.docx`。两者同时导出时，记录相同源 revision/baseline、各自 document_type/profile/version/content_hash。原件哈希、profile 版本、样式版本分别记录，不把排版变化误写成业务规则变化。

样式变化只产生新导出记录；若重组文字、章节或增删内容改变已确认 PRD 内容哈希，则走原有差异预览和版本确认机制，不要求重新询问所有已回答业务问题，也不能声称旧内容确认自动批准了新文本。MRD 的输出状态独立记录，不能把 PRD 内容确认伪装成 MRD 正式审核签字。

## 9. 本次修改的验收重点

正常 PRD／MRD 能按参考维度组织内容；允许合理精简；不能只靠标题字符串相等判通过。正常 Word 要真正生成和渲染检查，图示可见、表格不溢出、导航层级可用、页码／目录不沿用旧样例。

异常测试包括：模板样例污染、缺少调研数字仍被编造、把重要未知标为不适用、合并章节导致规则丢失、MRD 与 PRD 同一规则矛盾、无真人记录却填入已审核、profile 与文档类型不匹配、引用不存在的输出章节等。

详细冻结验收见 `03_ACCEPTANCE.md` 的 AT-15、AT-34、AT-37～AT-43 与 EV-09。参考 profile 校验或文档能打开都不等于真实模型成文质量已通过。
