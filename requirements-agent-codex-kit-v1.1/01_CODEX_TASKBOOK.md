# 多模态产品需求 Agent：Codex 开发任务书

版本：1.1｜日期：2026-09-23｜目标项目名：`requirements-agent`

## 0. 任务性质与成功定义

开发一个**独立、可启动、可持久化、可真实调用模型的产品经理需求 Agent**。不是只编写 Skill、Prompt、设计文档、固定模板或由 Codex 在运行时替产品做分析。

产品经理能够把零散文字、会议记录、网页网址、竞品截图、当前界面及现状描述交给系统。系统先理解材料，支持头脑风暴、对标与多视角审查，帮助用户作出必要决定，再形成 PRD 和低保真页面方案，并支持按需生成 MRD。Word 参考用户提供的两份模板的章节内容，允许适当合并、裁剪和增补，不照搬版式或示例业务。产品经理确认明确版本后，输出一致的前端 MD、后端 MD、验收条件和追踪数据，供现有 `ai-engineer-context` 及测试流程使用。

**Codex 是开发工具；DeepSeek 或用户配置的其它模型是产品运行时推理引擎。** 验收时关闭 Codex 辅助操作，用户仍须能通过应用完成核心闭环。

本任务书中“必须”属于冻结验收范围；“建议/默认”是实施默认值，不是未经用户确认的业务事实。发现技术矛盾应提出有证据的修正，不迎合、不静默扩大或缩小验收。

## 1. 用户体验与工作范围

### 1.1 目标用户

以企业 Web 管理系统产品经理为首批用户，兼顾开发和测试评审者。产品经理只需自然语言、现有材料和少量业务决策；不得要求其预先提供源码、CSS 选择器、接口 Schema 或完整清理规则。

### 1.2 两种显式模式，一个持续底稿

- **探索模式**：头脑风暴、竞品参考、现状改进、功能/交互备选。允许不完整和开放讨论；建议与已选范围严格分离。
- **收敛模式**：识别影响本期交付的关键缺口，澄清规则、权限、数据、异常和验收，准备 PRD 评审。

对标是两种模式均可调用的能力，不另建必须依次经过的流程。模式可随时切换；切换不能丢材料、重新问已回答的问题，也不能自动采纳头脑风暴建议。

页面线框和 PRD 草稿可以早期生成，用于帮助用户表达需求；未确认内容必须有标记。不能先强迫用户填完一份大问卷才能看到任何成果。

### 1.3 首次交互

用户提供材料后，先输出已有理解、材料读取状态、主要痛点及少量候选方向。每轮默认问不超过 3 个高价值问题，复杂时最多 5 个；每题说明“为什么现在需要决定”，尽可能给可选答案和差异。非阻塞问题先记录，不要无限追问。

用户提出不合理方案时，需要指出与其目标/约束的矛盾，给出替代方案；不要机械附和，也不要把自己的偏好当业务权威。

| RA-007 | 统一底稿及版本 | 来源、候选需求、规则、决策、问题、验收、UI 关系持久化；变更可追踪 |

| RA-009 | 参考章节的需求文档预览与导出 | 默认 PRD，支持按需 MRD／两者；对应 MD／DOCX 来自同版内容；参考原模板章节维度而非固定套填；状态标识真实 |

**不允许把 RA-003、RA-008 降为“以后支持”后宣称 V1 完成。** 没有可用视觉模型时可以诚实降级，但多模态验收仍为未完成。

## 3. 本期不做

不开发代码生成 Agent、全研发管理平台、全站无人爬虫、独立知识库/RAG 平台、复杂多 Agent 自治协作、企业 SSO、多租户 SaaS、Figma 高保真编辑器或完整设计系统。

不自动进入真实业务系统执行增删改，不自动发布或推送代码，不生成业务系统生产代码，不把 UI 预览当成业务实现。

不强制每次输出 MRD，不要求 MRD 先于 PRD；但按需 MRD 的 Word 导出能力属于本版范围。不替代测试 Agent 执行正式业务测试。测试交接只提供验收条件、测试关注点和需求关联。

登录态竞品/内网页面的自动探索列为后续能力；V1 用截图、导出文档和现状文字满足当前界面输入。不得通过用户浏览器存储或其它项目配置偷取登录态。

## 4. 默认技术方案与边界

默认采用 Python 后端 + 浏览器前端，避免核心业务逻辑全部写在前端语言中。

| 层 | 默认方案 | 约束 |
|---|---|---|
| 后端 | FastAPI、Pydantic、Python 稳定受支持版本 | 状态机、校验、业务底稿、模型适配在 Python |
| 前端 | React + TypeScript + Vite | 简洁中文工作台；不需要复杂微前端 |
| 存储 | SQLite + 本地受控文件目录 | 单机单用户优先；事务、迁移、版本和备份要可用 |
| 模型 | Chat Completions 兼容适配器 + DeepSeek 能力配置 | Provider 差异集中，不散落业务代码 |
| 网络材料 | HTTP 抽取；必要时 Playwright Python 渲染 | 确定性权限/地址/大小/时间限制 |
| 文档 | Markdown 渲染与 DOCX 导出器 | 内容来自相同版本，不分别让模型重写业务事实 |
| 验证 | pytest + Playwright E2E + 冻结语义评测 | 离线故障注入与真实模型验收分离 |

这是本项目实施默认值，不是必须依赖某个 Agent 框架。V1 采用单主控状态机、有限工具和阶段提示词即可。除非证明有必要，不引入 LangGraph、LangChain、向量库、Redis、Celery 或多模型投票。

依赖以实施时官方文档与实际环境验证为准，锁定版本。提供 Windows PowerShell 的安装、启动、停止和诊断脚本；不修改用户全局 Python、Node、代理或模型工具配置。

源代码和人工文档目录优先不超过 3 层；依赖、构建产物和运行数据自动目录不计入，不为满足层数把代码挤成一个大文件。

建议模块为 `models`、`workflow`、`sources`、`brief`、`review`、`ui_preview`、`exports`、`security`，可用文件或浅目录实现，不要求每个模块单独服务。

## 5. 模型接入：可替换不等于全部能力相同

### 5.1 已核实的接入起点

2026-09-23 查阅 DeepSeek 官方文档：OpenAI 格式基础地址为 `https://api.deepseek.com`；当前 `deepseek-flash` 支持视觉输入，`deepseek-v4-pro` 的视觉项为不支持。JSON Output 和 Tool Calls 有官方接口。具体依据见 `05_SOURCES.md` 的 S01-S05。

预置默认 `deepseek-flash`；Provider 和模型名不得写死在业务代码。模型别名可能更新，记录请求模型、响应模型和能力验证时间，不把别名视为不可变快照。

本包没有真实调用凭据，因此上述是文档核实，不是当前用户账号的 API 实测。

### 5.2 模型配置页

提供 Provider 显示名、协议类型、Base URL、模型名、密钥配置方式、连接测试、视觉支持、结构化输出支持、超时、上下文/输出预算及可选推理参数。密钥只在服务端使用。

首版“可更换”指已实现 Chat Completions 协议的兼容端点与模型；其它原生协议需要新增适配器，不能承诺仅修改 Base URL 即支持任意服务。

模型可手工输入，不能依赖 `/models` 返回一定存在或足以说明能力。能力状态区分 `documented`、`verified`、`unsupported`、`unknown`；“接口请求成功”与“任务语义效果合格”分开。

支持主分析模型与视觉模型使用同一配置，也允许分别指定。非视觉主模型通过经授权的视觉配置得到“带证据的图像观察”，不能把图片文件名或一段占位文本当成图片输入。

用户更换 Provider 后，展示新数据接收方，确认授权后再发送已有材料。禁止失败时悄悄切换到另一个付费/外部 Provider。

### 5.3 模型适配要求

统一返回最终内容、结构化数据、token 使用量、结束原因、实际模型、耗时和分类错误。提供非流式结构化请求作为初始可靠路径；UI 展示阶段事件进度，不伪造 token 流。

默认用**应用控制的阶段调用 + JSON 输出**，无需 V1 强制使用模型原生 Tool Calls。网页抓取和确认由应用路由控制，不伪造 tool_call 历史。以后启用原生 Tool Calls 时单独实现参数、关联 ID 和推理模式兼容测试。

JSON Output 只解决格式的一部分；必须另外做完整解析、Schema 校验、引用校验和语义审查。DeepSeek 文档提示可能返回空内容，输出截断也必须识别（S03/S05）。空串、截断、错误结构不得写入正式底稿。

不支持 JSON 模式的兼容端点允许“提示词要求 JSON + 严格本地验证”；最多 2 次受控修复，不得从杂乱文本中猜取片段并当成有效输出。保存错误摘要，不保存密钥或隐藏推理全文。

推理模式和 temperature 等参数按模型能力发送；不能认为所有兼容 API 参数均完全相同。初版结构化阶段默认非思考模式，可由配置改为已验证的思考模式。

## 6. 材料处理与真实性

每个材料有不可混淆的来源 ID、类型、标题、时间、哈希、版本、用途（现状/竞品/目标/模板）、读取状态和可定位片段。原件不可被模型覆盖，读取结果可重建。

必须区分：

- 材料中的陈述或截图可见内容。
- 当前产品经理提出的目标。
- 对竞品能力或隐藏交互的推断。
- AI 的建议与尚未确定的假设。
- 已有真人确认记录的本次产品规则。

“材料写过”“页面上有按钮”“某竞品采用这种设计”均不等于当前产品需求已被批准。时间、来源或材料之间有冲突时保留冲突，不以最新文字静默覆盖旧规则。

文本可定位到行/段落；DOCX 定位到标题、段落或表格；PDF 定位到页；图片定位到图片 ID 和可选区域；网页定位到 URL、抓取时间和冻结片段。引用只能使用本次实际可用的材料片段 ID。

图片优先视觉理解。OCR 不是默认主链路；如最终采用 OCR 作为降级辅助，需显式标注其只提取文字，不能据此认定理解了布局、图表或交互。扫描 PDF 可按需页面渲染后交视觉模型，不默默声称全文读取成功。

单个材料失败不阻止其它材料分析。系统必须显示 `PARTIAL`，解释本次判断的证据边界。无法访问网址时请用户提供截图/导出，但继续利用已读内容，不虚构抓取结果。

## 7. 头脑风暴、对标与澄清

头脑风暴应围绕用户的业务问题提出有意义的备选，不固定凑“三套看似不同实则换皮的方案”。复杂问题通常给 2-4 个方向；简单改动可以只给一个主建议和一个替代项。

每个方案包括目标用户/场景、主要路径、收益、牺牲、依赖、风险、本期最小范围、待确认假设和采用依据。能给推荐，但说明推荐建立在哪些已知约束上，不编造用户研究或市场份额。

对标输出“观察到什么 → 来源在哪里 → 与自身目标的关系 → 借鉴建议 → 哪些不能据此判断”。没有实际交互证据时，不推断后台权限、算法、性能、保存结果或认证情况。

用户选择方案后，只把所选部分作为待澄清候选；未选方案保留为 rejected/deferred，不混入本期 PRD。改口或撤回要保留变更记录。

澄清优先顺序：业务问题和目标 → 角色/场景 → 正常流程 → 关键规则/权限/数据 → 异常与边界 → 可验证验收 → 页面细节。顺序可根据已有信息调整，不能重复询问已经回答的问题。

## 8. UI 输出必须可看，而非只有描述

V1 必须支持由**受约束 UI JSON 结构**渲染成低保真预览，不能仅返回“建议采用简约风格”。

至少支持页面标题、导航/分区、筛选栏、表格/列表、表单、按钮、提示、对话框或详情面板、空态、加载态、错误态和权限态。按实际场景选用组件，不要求每一页都放齐。

可切换示例状态、打开/关闭模拟详情或弹窗；这些操作明确属于原型演示，不调用业务接口，不证明后端已经实现。未知字段/规则显示“建议/待确认”，示例数据显著标注为模拟。

所有功能性组件关联 REQ/AC 或候选条目；纯装饰组件可说明不关联。前端框架在此主要指页面/交互框架，不擅自替团队决定生产技术栈。

模型只能输出白名单结构和纯文本。渲染器禁止任意 JavaScript、HTML 事件、外部脚本、远程样式和不受控外链；下载 HTML 由可信模板生成，默认无网络请求。需要隔离预览时使用 sandbox iframe 和严格 CSP，不能只依靠提示词（S10）。

生成 UI 后做结构检查、浏览器渲染检查和业务映射审查。布局生成失败不应影响已保存需求；可单独重试这一阶段。

## 9. 统一底稿、PRD 与真人确认

底稿持久化背景、目标、角色、场景、需求、规则、验收、非目标、问题、来源、方案、UI 决策和版本关系。界面用中文卡片、表格与可编辑摘要展示，不暴露内部 Schema 给产品经理。

Word 内容参考 `references/` 中两份用户原件，具体见 `09_WORD_REFERENCE_RULES.md` 与 `references/content_profiles.json`。PRD 默认骨架为文档说明、产品介绍、产品说明、功能需求、非功能性需求；MRD 默认骨架为项目背景、名词解释、可行性分析、综合描述、功能详述、其它问题描述、附件。上述是章节内容参考，不是标题／章数／版式固定验收。

根据需求规模调整层级、合并、裁剪和补充；保留参考维度到实际章节的映射与理由。资料不足写待确认，不得为填满章节编造指标，也不能将相关未知标为不适用。逐功能仍考虑原型、流程、业务数据、接口依赖、边界和异常等适用维度。

PRD 仍须表达背景目标、现状、角色、范围/非目标、业务流程、逐功能规则、权限、数据和状态、异常边界、UI 说明、验收条件、依赖及待确认项；原模板没有独立标题的必要内容可整合或增补。模板中的示例角色、订单业务、字段长度、旧日期、审批签名、公司标识及静态页码不是当前项目事实。

PRD.md／PRD.docx 从同一 PRD 内容对象导出；MRD.md／MRD.docx 同理。两种文档可以侧重点不同，但须同版底稿、相同规范，不分别让模型重写业务规则。默认只选 PRD，用户按需选 MRD 或两者；不因此新增独立审批流程或强制双文档。

已有低保真页面应按同版 UI 关联嵌入“功能原型／页面布局”，标注模拟及未知。Word 导出必须实际打开／渲染检查，标题层级、表格、图示、分页和版本信息可用；不复刻旧模板视觉，也不能只验证文件存在。MRD 输出不代替 PRD 内容确认门禁。

产品经理可以直接编辑草稿；编辑转换成有差异预览的底稿变更。不能让 Word、Markdown 与 JSON 三套内容互相静默覆盖。V1 不要求自动理解任意 Word 修订；上传修订文档按新材料和变更候选处理。

确认页必须同时展示范围、关键规则、验收、重要待定项、文档/底稿版本及差异。用户按按钮确认指定版本；聊天中的“可以”“不错”、模型文字“用户已确认”不得直接改变确认状态。

确认绑定 `project_id + draft_revision + brief_hash + prd_content_hash + ui_spec_hash`。服务端生成 confirmer、时间和记录 ID；前端提交哈希只是并发控制输入，服务端必须重新核验。

**内容确认不是技术设计通过、测试通过或业务上线批准。** 文档应写“产品经理内容确认”，不得伪造正式审核签字。

重大业务规则或验收阻塞项未解决时，不允许标为可研发基线。用户可以缩减范围后确认已明确的子集；未知非阻塞事项允许保留，需标明责任与影响。

## 10. 前后端及测试交接

仅在指定需求基线有效且已确认时生成正式交接包：

```text
handoff/
  README.md
  requirements.md
  frontend_spec.md
  backend_spec.md
  acceptance_criteria.md
  open_questions.md
  ui_spec.json
  prototype.html
  traceability.json
  manifest.json
```

README 写明基线、内容确认状态和使用方法。`requirements.md` 保存共同业务规则；前后端文档引用相同 REQ/AC，不分别重述成不同规则。技术建议标注待开发确认，不擅自编造数据库表、接口路径、枚举或事务承诺为已定方案。

`acceptance_criteria.md` 写测什么、前提、操作/触发、可观察结果和边界；定位器、执行脚本及真实测试报告由下游测试能力承担。

`manifest.json` 记录 schema_version、需求基线 ID/哈希、确认记录 ID、生成器/提示词版本、各产物哈希与内容角色。模板升级重排版也生成新导出记录，不能覆盖旧包。

对接 `ai-engineer-context` 时保留上游 REQ/AC，不猜测本地 Skill 私有格式。能读取授权工作区实际规范时做适配；找不到时输出中性包并明确“适配未验证”，不改写已有治理目录、不重建历史事实。

任一已确认业务行为在派生文档中被增加、弱化、遗漏或改为相反含义，应阻止正式交接包发布并显示冲突；“有同一个 REQ ID”本身不足以证明语义一致。

## 11. 变更与并发

确认版本不可变。新增材料、聊天或修改产生新的草稿/候选变更，不能直接写入历史基线。

变更分析列出新增、修改、删除、保持的条目，以及受影响的 UI、PRD、前端/后端和 AC。与本期业务无关的材料不自动导致全量重确认；明确指出是否影响当前基线。

采用变更并建立新基线后，旧导出保留并显示“历史版本/相对新基线过期”；不能覆盖旧报告或删除旧批准证据。已在生成中的旧任务提交前核验 revision，过期产物只允许作为旧版产物保存，不能冒充当前正式版本。

生成、确认、导出及续跑请求支持幂等键。两个浏览器标签页同时编辑时，过期请求得到清晰冲突，不覆盖最新内容。

## 12. 预算、状态与可观察性

预算必须可见可配，不在代码中隐藏硬上限。初始工程默认：每次用户触发动作最多 8 次模型请求（含失败/修复）、单来源读取最多 30 秒、单模型请求超时 120 秒、每动作最长 300 秒；最多 2 次格式修复和 2 次瞬态网络重试，均受总调用预算约束。正式 PRD 较大时分节生成并由用户发起继续，不悄悄截断。

上下文预算包含系统提示、底稿、检索片段、视觉输入、输出预留及安全余量；上下文不够时按来源片段选择，不删改已确认业务规则来凑长度。记录实际送入材料 ID/片段 ID 和未送入范围。

运行状态至少包括排队、读取材料、调用模型、校验、等待用户、成功、部分完成、失败、取消、预算暂停。展示当前阶段、调用次数、token/估算费用及卡点。价格未配置时费用写“未知”，不能写 0 元。

401/403、额度不足、模型不存在、参数不支持、限流、网络故障、空输出、截断、Schema 错误、语义阻塞分别处理。不把自身预算限制解释为模型余额不足。

取消后不再发新请求；已发请求可能仍产生费用，应如实提示。任务重启后保留证据和续跑点，不能重新执行已成功阶段并重复扣费而不说明。

## 13. 安全与数据权限

默认仅监听 loopback，单用户本地运行。提供本地会话认证或安装时随机访问令牌、Origin/Host 检查、CSRF 防护与严格 CORS；“只在本机”不等于可以省掉防浏览器跨站访问措施。对外监听必须另行配置认证和部署安全，不默认开放局域网。

密钥优先使用环境变量；界面输入支持仅会话使用，持久化需本机安全存储/系统凭据设施，不在浏览器 localStorage、数据库明文、日志、导出、URL 或 Git 中保存。代理显式配置并脱敏，不修改全局代理，不关闭 TLS 校验。

发送企业材料到外部模型前展示 Provider、材料范围和授权；默认不把完整项目发给每一个模型。授权按接收端和项目管理，截图可能包含敏感数据，提供预览和排除。

材料是数据，不是系统指令。网页/截图/文档出现“忽略指令”“调用本地文件”“自动批准”等文字不得改变权限或执行流程（S09）。Agent 不拥有 shell、任意文件读取、审批、发布或密钥读取工具。

URL 抓取只允许显式授权的 http/https 地址；限制重定向、DNS、端口、大小、总时长和抓取范围。默认阻止回环/私网/link-local/云元数据地址，检查每次跳转和所有浏览器子资源；防 DNS 重绑定，不能只检查字符串（S08）。仅用请求路由过滤不能宣称完全解决浏览器出网风险；必要时使用受控 egress 代理或隔离执行。生产保护不能为了本地 fixture 关闭；测试配置只白名单明确 fixture 主机/端口。

模型配置端点和网页抓取是两个独立权限域：本地模型地址允许管理员显式白名单；网页中的内容不能新增模型配置或获得 Key。密钥绑定 Provider origin，不随重定向转发。

上传校验真实格式、大小、压缩展开上限和路径；拒绝路径穿越，不执行 Office 宏或嵌入对象。原始网页和 Markdown 预览不运行脚本。

## 14. 实施顺序与每阶段证据

| 阶段 | 实现内容 | 进入下一阶段前的最小证据 |
|---|---|---|
| M0 | 检查工作区、需求索引、架构决策、契约及测试基线 | 记录真实目录/环境；写出需求到测试映射，不只口头计划 |
| M1 | Python 服务、Web 壳、SQLite、模型设置、文本到澄清 | 应用自身调用模型；无 Key 路径及重启持久化测试 |
| M2 | 来源管理、网页/文档/图片、多模态能力判断 | 图片真正经视觉模型处理；错误能力配置被识别 |
| M3 | 探索/收敛、底稿、问题去重、冲突与差异 | 选中/拒绝方案不混淆；新旧规则冲突被检出 |
| M4 | UI 结构预览、PRD／MRD 章节参考和 MD／DOCX 导出、确认与版本门禁 | 参考内容映射、正常／精简文档、样例污染反例及真实 Word 渲染；过期确认拒绝 |
| M5 | 交接包、追踪、变更失效、恢复与预算 | 同版导出一致；变更后旧版标识正确；不伪造完成 |
| M6 | 全量自动化与真实模型评测、真人首审材料 | `03_ACCEPTANCE.md` 要求的实际报告和证据 |

每阶段都交付可运行增量。不得先堆完整漂亮前端，再把核心分析、存储和审批留成占位函数。

不使用真实企业敏感资料充当默认测试数据。冻结合成 fixture 后再开发；修改 fixture 的业务预期必须说明理由并获得对应授权，不为让结果通过而删减难例。
